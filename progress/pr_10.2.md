## Overview

Task 10.2 completes subject verification for the delivered simulation. It combines full-binary checks of the EDF viability boundary and observable behavior with a focused correction to fixed CLI output, then adds repeatable evaluation scenarios for symbol, global-data, memory, and race checks.

## Approach

The task uses acceptance tests against the executable and compiled objects to check the rules evaluators can observe. The first two subtasks exercise the sufficient EDF bound and log-visible scheduling rules. The third replaces fixed-text formatted output that introduced a disallowed binary symbol while preserving the output bytes. The final subtask adds two EDF configurations to the root development Makefile's Memcheck and ThreadSanitizer scenario list. The root Makefile remains development tooling, separate from the delivered `coders/Makefile`.

## Decisions

The phase review moved scheduling-sensitive below-bound outcomes out of mandatory pass/fail criteria and kept them as empirical evidence. The user accepted the observed below-bound burnouts for documentation because the startup offset is a heuristic and the sufficient viability bound makes no guarantee for those inputs. Exact FIFO/EDF request ordering remains covered by the phase 06 API-level oracles because it cannot be inferred from the public log.

## Issues resolved

**Phase 10 verification scope needed stronger evidence.** The phase gate found incorrect boundary arithmetic and an unsupported ticket-order claim in 10.2.1, a 1 ms startup timing assumption in 10.1.2 and 10.2.4, incomplete detection of internal file-scope globals, and Valgrind criteria that did not ensure the tool really ran and returned the target's expected status. These could make required checks flaky or let relevant violations pass. The phase plan and specs were revised to use the actual sufficient-bound values, make scheduling-dependent runs empirical, inspect internal and external file-scope data while allowing function-local statics, and check real Valgrind execution and target statuses; the phase gate then approved the sealed plan.

**Two full-binary log oracles admitted malformed IDs or hidden output.** Code review found that 10.2.1 AC6 parsed a NUL-terminated string despite retaining the complete byte count, and 10.2.2 narrowed a `strtol` result before checking its permitted range. Both defects could let invalid acceptance output pass. The acceptance tests were corrected and resealed through their plan gates; the subsequent code reviews approved them without changing production behavior or acceptance criteria.

**Below-bound empirical runs sometimes burned out.** Ten-run samples showed one burnout in the `5 800`, `4 610`, and `4 410` scenarios. These inputs are below the sufficient bound and the startup offset does not guarantee a thread schedule. After the result was raised, the user chose to accept and document the observations rather than treat them as evidence against the bounded guarantee. The implementation report and 10.2.4 reference note retain the counts and decision.

**Nested Valgrind did not supervise the oracle cleanly.** An implementation attempt wrapped the acceptance oracle in Valgrind even though that oracle launches Valgrind for AC5; the nested run returned 134. The required memory evidence instead comes from `make memcheck` running the configured target scenarios directly, which exited 0, as did `make tsan`. No product or oracle change was needed for this tooling issue.
