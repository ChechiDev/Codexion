No test needs `fflush` or `setvbuf`: the logger does not use stdio.

Code review check: an invalid `state` returns before any lock; lock order `log_mutex → stop_mutex`; every mutex result is checked and only locks acquired by this call are unlocked; on a `stop_mutex` unlock failure it skips writing and still attempts the `log_mutex` unlock; `stop_mutex` is released before `write`; the timestamp is read after `log_mutex` is acquired; if `ts == -1` or `len == -1`, `write` is not called; the line is built by `build_log_line` (3.4.2) and sent with exactly one `write(1, line, len)` while holding `log_mutex`, with no retry; success requires `write` to return `len`; on a clock, build or `write` failure the `log_mutex` unlock is still attempted; no stdio output function is used; message texts are exactly the subject's (5.1.1); functions stay within the Norm (25 lines, 4 parameters, 5 functions per file; small static helpers allowed).

## Description

**Type.** `main.h` gains in Types:

    typedef enum e_state
    {
        STATE_TAKEN_DONGLE,
        STATE_COMPILING,
        STATE_DEBUGGING,
        STATE_REFACTORING
    }   t_state;

The four ordinary state changes of a coder. `burned out` is not here: it is the
terminal line, printed by `print_burnout` (3.4.4) together with the stop.

**Function.** `int print_state(t_sim *sim, int coder, t_state state)` in
`coders/src/log/print_state.c`, prototype in the `Log` section of `main.h`
(created by 3.4.2). `<unistd.h>` is included in the `.c` file.

**Preconditions (from 3.2.1).** `sim` is a valid, initialised `t_sim`;
`start_ms` does not change while threads log; the caller holds neither
`log_mutex` nor `stop_mutex`. `coder` is the 1-based coder number (subject 5.3);
a value below 1 is rejected by `build_log_line` (no duplicate check here), and
checking the upper bound `number_of_coders` is the caller's job.

1. Invalid `state` → return -1, nothing written, no lock taken.
2. Lock `log_mutex`; lock `stop_mutex`; read `stopped`; unlock `stop_mutex`.
3. If stopped → unlock `log_mutex`, return -1.
4. `ts = get_elapsed_ms(sim->start_ms)` (3.1.2); `len =
   build_log_line(line, ts, coder, text)` (3.4.2) into a local
   `char line[LOG_LINE_MAX]`. If `ts == -1` or `len == -1`, skip the `write`,
   attempt to unlock `log_mutex` and return -1 (a negative length must never
   reach `write`).
5. `write(1, line, len)` once; unlock `log_mutex`; return 0 only if `write`
   returned `len`.

The texts live in a local `static const` table indexed by `state` (no
globals), with the subject's exact spelling.

**Why this order.** Reading the timestamp inside `log_mutex` makes the
timestamps non-decreasing in output order (unless the wall clock jumps
backwards, 3.1.2). Checking `stopped` inside `log_mutex`, together with
`set_stopped` (3.2.2) and `print_burnout` (3.4.4) taking `log_mutex` first,
guarantees no state line is written after the stop. `stop_mutex` is released
before writing, so `is_stopped` callers never wait for output.

**Output: one unbuffered `write` per line** (PLAN.md "Log", user decision
2026-10-28). There is no stdio buffer, so a line is visible to a terminal or a
pipe reader as soon as the call returns (AC2), and all lines keep their order
because they all take the same path. A line is at most 64 bytes, well under
`PIPE_BUF`, so a successful `write` of it cannot interleave with another
writer on the same pipe (pipes keep no message boundaries; readers may still
split it across reads).

**No retries.** A short `write` or -1 (including `EINTR`) is a failure: the
`log_mutex` unlock is attempted and -1 returned. That keeps exactly one `write`
per line.

**Return contract (follows `docs/conventions.md`).**
- 0: the whole line was written (`write` returned `len`) and every unlock
  succeeded.
- -1: the line was rejected (stopped, invalid state, coder below 1) or
  something failed (a mutex operation, the clock, or `write`).

"Nothing written" is guaranteed only for rejections and failures before
`write`: a short or failed `write` may leave partial output, and an unlock
failure can follow a successful write.

**README.** No close-time update: no user-visible behaviour changes until the
coders log through the binary (phase 09).
