## Description

`int set_stopped(t_sim *sim)` in `coders/src/state/set_stopped.c`: marks the
simulation as stopped. It locks `log_mutex`, then `stop_mutex`, sets
`stopped = 1`, and unlocks in reverse order.

**Preconditions (from 3.2.1).** `sim` is a valid, non-NULL `t_sim` whose
mutexes are initialised (default, non-robust), and the caller holds neither
`log_mutex` nor `stop_mutex`. AC4 and AC5 break the ownership precondition on
purpose, with test-only `PTHREAD_MUTEX_ERRORCHECK` mutexes, only to exercise
the defined failure paths.

**Why it takes `log_mutex` too.** `print_state` (3.4.3) checks `stopped` and
prints while holding `log_mutex`. If `set_stopped` took only `stop_mutex`, a
logger could read "running", lose the race to `set_stopped`, and still print a
line after the stop. Holding `log_mutex` while setting the flag makes every
state line either fully before the stop or not printed at all.

**Scope.** It is the plain stop used when every coder reached
`number_of_compiles_required` (phase 08). It prints nothing and wakes no
thread: broadcasting the dongle `cond`s belongs to phases 06/08.

**Terminal-state protocol (for 3.4.4 and phase 08).** `print_burnout` (3.4.4)
does not call `set_stopped`: it checks `stopped`, performs the first stop and
prints, all under the same `log_mutex → stop_mutex` order. If `set_stopped`
wins, the burnout prints nothing; if the burnout wins, a later `set_stopped`
succeeds idempotently. Lock order alone does not decide which event has
priority when both are due at once (including `number_of_compiles_required =
0`): the single monitor of phase 08 defines that choice.

**Error contract (follows `docs/conventions.md`).** Returns 0 on success, -1 if
any mutex operation fails:
- `log_mutex` lock fails → returns -1, nothing changed.
- `stop_mutex` lock fails → attempts to unlock `log_mutex`, returns -1,
  `stopped` unchanged.
- after the assignment, both unlocks are always attempted (`stop_mutex`, then
  `log_mutex`); if either fails it returns -1. `stopped` stays 1 (no
  rollback), and a mutex is released only if its own unlock succeeded.

So -1 alone does not tell whether the stop happened. After a failed unlock a
mutex may still be held, so a caller cannot safely assume that another locking
read (`is_stopped`) is possible; it treats -1 as a fatal synchronisation error
and ends its work (the shutdown path belongs to phases 08-09). Unlock failures cannot be induced safely under the valid-use
invariants, so they are not acceptance-tested; the code gate checks them by
source review (Code review check above).
