## Description

`int build_log_line(char *line, long ts, int coder, const char *text)` in
`coders/src/log/build_log_line.c`: builds one log line `<ts> <coder> <text>\n`
(subject 5.1.1 format) at the start of `line` and returns its length. It is the
single place that knows the line format; `print_state` (3.4.3) and
`print_burnout` (3.4.4) call it and send the result with one `write` (PLAN.md
"Log").

It is pure (core logic inside the `log/` module, which depends on the core
`utils/` helper): no output, no lock, no clock, no allocation, so the format is
tested without threads or pipes. Close-time documentation: `docs/architecture.md`
gains the `log/` row, noting this pure helper.

**Preconditions.** A non-NULL `text` points to a `'\0'`-terminated string whose
storage does not overlap `line`; a non-NULL `line` provides at least
`LOG_LINE_MAX` writable bytes (the signature cannot check capacity).

- **Capacity.** `LOG_TEXT_MAX` is 32 (the longest subject text,
  `has taken a dongle`, has 18) and `LOG_LINE_MAX` is 64 = 19 (`LONG_MAX`
  digits) + 1 + 10 (`INT_MAX` digits) + 1 + 32 + 1 (`'\n'`), so every valid
  line fits (LP64, as 3.4.1).
- **Validation first.** It returns -1 and writes nothing if `line == NULL`,
  `text == NULL`, `ts < 0`, `coder < 1`, the text is empty, longer than
  `LOG_TEXT_MAX`, or contains `'\n'` or `'\r'`. So every successful call
  produces exactly one physical line.
- **No terminator.** It writes no `'\0'`; the caller passes the returned length
  to `write`.

**Return contract.** Same justified exception as 3.4.1 (user decision,
2026-10-28): the length (>= 6, since the text is not empty) or -1, so the
caller can pass it straight to `write`.

`main.h` gains a `/* ---- Log ---- */` section after `State` and before `CLI`.
