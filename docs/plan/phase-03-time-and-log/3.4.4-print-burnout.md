## Description

`int print_burnout(t_sim *sim, int coder)` in `coders/src/log/print_burnout.c`:
the terminal log line. It performs the **first** stop of the simulation and
writes `<ts> <coder> burned out` in one critical section, so nothing can be
written after it (subject 5.1, PLAN.md "Log"). It is called by the monitor
(phase 08) when it detects a burnout.

Preconditions as in 3.4.3 (valid `t_sim`, immutable `start_ms`, caller holds
neither mutex, `coder` 1-based; below 1 is rejected by `build_log_line`).

1. Lock `log_mutex`; lock `stop_mutex`.
2. If `stopped` → unlock both, return -1 (someone already ended the run).
3. Set `stopped = 1`; unlock `stop_mutex`.
4. `ts = get_elapsed_ms(sim->start_ms)`; `len = build_log_line(line, ts, coder,
   "burned out")` into a local `char line[LOG_LINE_MAX]`. If `ts == -1` or
   `len == -1`, skip the `write`, attempt to unlock `log_mutex`, return -1.
5. `write(1, line, len)` once; unlock `log_mutex`; return 0 only if `write`
   returned `len`.

**Terminal-state protocol** (3.2.2): if `set_stopped` won, the burnout writes
nothing (AC4); if the burnout won, a later `set_stopped` is idempotent (AC5).
Choosing between a due burnout and "all compiled" is the monitor's job
(phase 08).

**Return contract (follows `docs/conventions.md`).**
- 0: this call made the first stop, the whole line was written and every
  unlock succeeded.
- -1: nothing to do (already stopped) or a failure. Once step 3 ran, the stop
  stays committed (`stopped == 1`) even if the clock, the line build (AC9),
  `write` or an unlock then fails. A -1 may follow partial output; a mutex is
  released only if its own unlock succeeded.

**Output and the 10 ms rule.** One unbuffered `write` (PLAN.md "Log"): the line
is visible to a terminal or a pipe reader as soon as the call returns (AC2), not
at program exit, so its visibility does not depend on shutdown time. The
end-to-end limit (subject 5.1.3: shown within 10 ms of the real burnout) also
depends on the monitor's detection cadence (phase 08), lock contention,
scheduling and output backpressure; phase 10 verifies it by reading a live
pipe from the unmodified binary.

**README.** No close-time update (no user-visible change until phase 09).
