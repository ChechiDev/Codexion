`S` is the timing slack in ms read from the `CODEXION_TIME_SLACK_MS` environment variable (default 0; CI exports 40). It is added to upper bounds only, never to lower bounds. The timing ACs assume no backward wall-clock adjustment during the test.

Code review check: with `ms <= 0` it calls no clock, mutex or `usleep`; no mutex is held across `usleep`; every clock read (initial and in the loop) is checked for -1 before any subtraction; each slice is at most `SLEEP_SLICE_US` and never longer than the remaining time, with the remaining milliseconds capped before multiplying by 1000 (no overflow for large `ms`); the elapsed time is re-read from the clock after every slice (no counting of requested sleeps); a failed `usleep` is handled by continuing the loop.

## Description

`int sleep_ms(t_sim *sim, long ms)` in `coders/src/time/sleep_ms.c`: waits `ms`
milliseconds in short `usleep` slices (allowed; `<unistd.h>` in the `.c`),
checking the stop flag between slices so a coder never sleeps through the end
of the simulation. Preconditions are those of 3.2.1: valid, initialised
`t_sim`, and the caller holds neither `stop_mutex` nor `log_mutex`.

1. `ms <= 0` → returns 0 immediately.
2. `start = get_time_ms()` (3.1.1); -1 → return -1.
3. Loop: if `is_stopped(sim)` (3.2.1) → return -1. Read `now = get_time_ms()`;
   -1 → return -1. If `now - start >= ms` → return 0. Otherwise
   `usleep(min(SLEEP_SLICE_US, remaining µs))`.

**Slice.** `SLEEP_SLICE_US` is 500 (a `main.h` macro): it requests slices of
at most 500 µs, so a stop is noticed quickly; the actual latency depends on
scheduling and contention. Nominally that is up to about 2,000 wake-ups and
stop checks per second per sleeping coder (400,000/s with 200 coders); phase 10
measures that cost. The slice alone does not guarantee the 10 ms burnout limit
(subject 5.1.3): that is end-to-end, owned by the monitor (phase 08).

**Return contract (follows `docs/conventions.md`).**
- 0: the duration was reached (in project-clock milliseconds), or `ms <= 0`.
- -1: the stop was observed (including a mutex failure inside `is_stopped`,
  which reports "stopped", 3.2.1) or the clock failed (`get_time_ms` returned
  -1, 3.1.1). Since the stop is checked first, -1 is possible even if the
  duration had just elapsed.

Callers react the same way to -1: abandon the current action. A failed
`usleep` (e.g. `EINTR`) is not an error: the loop re-reads the clock and goes
on.

**Limitation.** `gettimeofday` is wall-clock time: if it jumps backwards
during a sleep, the sleep lasts longer by that amount (same limitation as
3.1.2). Clock and `usleep` failures cannot be induced without test-only fault
injection, so they are checked by source review (Code review check above).
