## Vision

`codexion` is the 42 *Codexion* project (subject: `docs/codexion-rules.md`, binding):
a C simulation where N coders (one POSIX thread each) sit in a circle and share N
USB dongles. Compiling needs both neighbouring dongles; a separate monitor thread
ends the run on the first burnout (logged within 10 ms) or when every coder has
compiled `number_of_compiles_required` times. Dongles are arbitrated by a
hand-written priority queue under a `fifo` or `edf` policy, with a mandatory
cooldown after each release.

## Goals

- Pass the 42 evaluation: subject-compliant behaviour, Norm-clean, no crashes,
  no leaks, no data races, allowed functions only, no globals.
- Strict, total input validation: no input can crash or hang the program.
- Under `edf`, nobody burns out when the parameters are viable.
- Every behaviour covered by tests (unit + full-binary simulation tests).
- A didactic, conversational README that meets subject section 7.

## Scope

- **In:** mandatory part only: argument parsing/validation, `t_sim` init and
  teardown, time and serialized logging, priority queue (heap), dongle
  arbitration with cooldown, coder threads, monitor thread, lifecycle,
  deliverable `coders/Makefile`, CI (norminette + build + tests + valgrind + TSan),
  README.
- **Out:** bonus part (the subject defines none), libft, any function outside the
  subject's allowed list, a cap on `number_of_coders`.

## Architecture overview

**Deliverable layout** (subject 6.1: `Makefile`, `*.c`, `*.h` in `coders/`):

```
coders/
  Makefile                 deliverable: cc -Wall -Wextra -Werror -pthread, NAME/all/clean/fclean/re, no relink
  main.c  main.h           entry point; the single header (types, prototypes, constants)
  src/<module>/*.c         utils · parsing · cli · init · time · log · heap · dongle · coder · monitor · lifecycle · cleanup
```

The repo root (`Makefile`, `harness/`, `docs/`, `tests/`, `progress/`) is dev
tooling and is **not delivered**. The root `Makefile` keeps the harness contract
(`check/verify/test/lint/plan/status`) and delegates the build to `make -C coders`;
tests link the `coders/` objects except `main.o`. `harness.toml` sets
`src_dirs = ["coders"]` so the scope guard covers `coders/`.

**Layers and dependency direction** (`docs/architecture.md`):

| Layer | Modules (`coders/src/<module>/`) | May use |
|---|---|---|
| Core (pure) | `utils` (generic helpers, no domain knowledge), `parsing` (string → config, validation rules), `heap` (min-heap of requests), `policy` (fifo/edf key, request ordering, viability-free arithmetic) | `main.h` types, `strcmp`/`strlen`/`malloc`/`free` only; **no** pthread, clock or output |
| Adapters (platform) | `time` (`gettimeofday`, sliced `usleep`), `log` (mutex-serialized, one unbuffered `write` per line), `init`/`cleanup` (mutex/cond/alloc lifecycle) | core + pthread/clock/output |
| Orchestration | `dongle` (two-heap acquisition/release), `coder` (thread routine), `monitor` (thread routine), `lifecycle` (start/join threads and drive a simulation run) | core + adapters |
| Interface | `main.c` (argv → parse → exit codes → run), `cli` (usage and argument error messages) | everything below |

Dependencies point inward only: core never includes or calls adapters or
orchestration, so parsing and heap are unit-testable without threads or time.

**Living files:** `coders/Makefile`, `coders/main.h` and `README.md` grow with each
subtask that adds sources, prototypes, types or user-visible behaviour.

**Concurrency design (approved in discovery):**

- **State:** one `t_sim` (args, coders, dongles, monitor/stop state, log mutex)
  passed by pointer; no globals.
- **Dongle:** `mutex` + `cond` + own request heap + `available` + `released_at`
  (cooldown). Granted only to its heap head once the cooldown has elapsed; waits
  use `pthread_cond_timedwait` (no busy-wait).
- **Arbitration keys:** `fifo` = monotonically increasing arrival ticket;
  `edf` = `last_compile_start + time_to_burnout`, ties broken by arrival ticket.
- **Acquisition: both dongles at once (no hold-and-wait).** A coder pushes one
  request with the same `(key, ticket)` into the heaps of both its dongles. It
  takes them only when it is the **head of both heaps** and both are available
  with their cooldown elapsed; then it pops itself from both and takes both in
  one step. It never holds one dongle while waiting for the other, which breaks
  Coffman's *hold-and-wait*. The two dongle mutexes are always locked
  lower-index first, so the short check-and-take critical section cannot
  deadlock either.
- **Progress argument:** `(key, ticket)` is a strict total order and a request
  carries the same key in both heaps, so the waiting coder with the globally
  smallest key is the head of both its heaps. Nobody else can take its dongles;
  it compiles as soon as its neighbours finish (at most `time_to_compile`) plus
  `dongle_cooldown`. Hence no deadlock and no starvation under either policy.
  Under `edf` the smallest key is the closest deadline, so the most urgent
  coder is always the next to be served around its seat.
- **Viable parameters (the `edf` no-burnout guarantee, subject 6.1.6).** Write
  `C = time_to_compile`, `D = dongle_cooldown`, `R = time_to_debug +
  time_to_refactor`, `B = time_to_burnout`. Sufficient condition:
  `N >= 2` and `B >= C + R + N * (C + D) + margin` (`margin` = 10 ms of
  scheduling slack). `N = 1` is never viable (one dongle). Service bound under
  `edf`, for a coder `c` that last started compiling at `s` (or 0 at start-up)
  and requests at `r = s + C + R`:
  1. A dongle heap only ever holds requests from the two coders sharing it, so
     `c` is blocked only by its neighbours. A neighbour can take a dongle of `c`
     while `c` waits only if it heads both its heaps, i.e. its key is smaller
     than `c`'s.
  2. No request with a key smaller than `c`'s can appear after `r`: a smaller
     key means an earlier last start `s' <= s`, so that coder requested at
     `s' + C + R <= r` (every coder has the same `C + R`; equal keys fall back
     to the earlier ticket). The set `S` of requests ahead of `c` is fixed at
     `r` and has at most `N - 1` members; a served member gets a new key
     `>= r + B > c`'s key, so each member is served at most once before `c`.
  3. At any time the smallest-key waiter `e` of `S ∪ {c}` heads both its heaps
     (no new smaller key can arrive, by 2). Its dongles can only be busy with a
     compile already in progress (at most `C`) and then cooldown (at most `D`),
     so `e` starts compiling within `C + D` (plus wake-up latency, in `margin`).
  4. Repeating 3 for at most `N` epochs (the `N - 1` members of `S`, then `c`),
     `c` starts compiling by `r + N * (C + D)`, which is before its deadline
     `s + B` when the condition above holds.
  The same argument with ticket keys gives the starvation-freedom of `fifo`
  (no burnout guarantee there). The bound is conservative on purpose: typical
  evaluation runs below it (e.g. `5 800 200 200 200 ... edf`) are tested
  empirically in phase 10 but not claimed as guaranteed; it is a sufficient
  condition, not the definition of every viable input. A run whose repeated
  cycle `C + R` exceeds `B` can never survive (`4 410 200 200 200` has a 600 ms
  cycle). Timing assumptions: the bound assumes that a coder requests at
  `s + C + R` and wakes within `margin`, so an operating system that delays a
  thread beyond `margin` is outside it. The one-time start-up offset of even
  seats (below) only delays a first request by `START_TURN_MS`, also counted in
  `margin`: those requests carry the initial key with a later ticket, so the
  order argument does not change. The argument above is
  the proof; tests are evidence over finite scenarios. Phase 06 tests the
  arbiter in isolation (head-of-both rule, ordering, cooldown, wake-up on
  stop). Full-binary no-burnout runs at and above the viability boundary
  (including an `N = 6` case; ticket order stays covered by phase 06) belong
  to phase 10, once the coder, monitor and lifecycle exist.
- **Start-up offset:** even seats wait `START_TURN_MS` (1 ms, compile-time macro)
  once before their first request, so non-neighbouring coders usually compile in
  parallel from the start instead of chaining in seat order. A heuristic with no
  effect on arbitration: if the system delays an odd thread longer, the start-up
  falls back to the serial order, which is still safe.
- **Coder thread:** take dongles, `compiling`, release, `debugging`, `refactoring`,
  loop. A per-coder mutex guards `last_compile_start` and `compile_count`.
- **Monitor thread:** scans about every 1 ms. On burnout it logs, sets `stop`
  under a mutex and broadcasts every dongle `cond`; it also detects "all coders
  reached the compile target".
- **Sleep:** `usleep` in short slices that check `stop`.
- **Log:** one output mutex; `stop` is checked inside it, so nothing is printed
  after the end except the `burned out` line itself. Each line is built in a
  local buffer (decimal numbers formatted by a `utils` helper, since `snprintf`
  is not allowed) and sent with a single `write` to stdout while holding the
  mutex. No stdio buffering: a line is visible as soon as it is written, also
  on a pipe, so the burnout line can meet the 10 ms limit (subject 5.1.3)
  without depending on shutdown time (`fflush` is not allowed), and every line
  keeps its order because all of them take the same path. (User decision,
  2026-10-28, replacing the earlier `printf` logger.)
- **Edge cases:** 1 coder means 1 dongle: it takes it, logs it, and burns out at
  `time_to_burnout`. `number_of_compiles_required = 0` ends immediately and
  cleanly.

**Input validation (strict):** exactly 8 args. Numbers: leading and trailing
whitespace (the six C-locale `isspace` characters) is trimmed by one shared,
reusable helper, without copying or modifying `argv`; what remains must be
digits only (no sign, inner whitespace, empty, hex, decimals; leading zeros
allowed); each value `<= INT_MAX` with a custom overflow-safe parser;
`number_of_coders >= 1`, `time_to_burnout >= 1`, other times and the compile
target `>= 0`. Scheduler: exactly `fifo` or `edf` (subject: case-sensitive, no
trimming). Any error prints a specific `Error:` line plus the usage to `stderr`
and exits non-zero before allocating anything or starting threads.
`malloc`/`pthread_*` failures shut down cleanly (join what was
started, free everything, exit non-zero).

> Trimming whitespace around numbers is a user decision (2026-10-27); these
> input-normalisation rules may change in the future.

**Tests:** `assert.h` with one runner per file (`tests/unit/`, `tests/acceptance/`).
Unit tests cover pure functions; simulation tests run the binary and check the
log (format, ordering, unmixed lines, burnout within 10 ms, cooldown,
`fifo`/`edf`). CI adds valgrind (leaks) and a `-fsanitize=thread` build (races),
with wider timing tolerance than local runs.

**Key risks:** timing precision on loaded machines (burnout ≤ 10 ms), the
two-heap "head of both" logic (lost wake-ups, stale heads after stop; covered by
phase 06 tests), Norm limits (25 lines/function, 5 functions/file, 4 params)
shaping the module split.

**Setup before phase 01 (leader, on `chore/project-setup`, not product code):**
`harness.toml` (user), root `Makefile` adapted to `coders/` (norminette as lint;
no clang-format, it conflicts with the Norm), CI extended to build + `make check`
+ valgrind + TSan.

## How this folder works

```
docs/plan/
  PLAN.md                                 this file (vision… + generated index)
  phase-NN-<slug>.md                      one per phase: title, goal, its tasks N.M
  phase-NN-<slug>/<N.M.K>-<slug>.md       one spec per subtask (micro-task)
```

- **Every phase exists from the start** with its title and goal, so the whole
  scope is visible and reviewed (roadmap gate).
- **One phase at a time**: phase N+1 gets its tasks and specs only when phase N
  is done (`make check` enforces it).
- **Status lives only in the subtask specs.** Task / phase status,
  `feature_list.json` and the index below are derived by `make plan`.
- Approved plans are **sealed**: editing what Codex approved (except `status`)
  fails `make check` until the gate approves the change.
- `make status` shows the whole plan, every gate verdict and the next step.

Ids: phase `NN` · task `N.M` · subtask `N.M.K`. They are used everywhere else
(`feature_list.json`, `progress/`, `docs/reference/<N.M.K>-<slug>.md`, commit
footer `Plan: docs/plan/phase-NN-<slug>/<N.M.K>-<slug>.md`).
