## Description

`int set_compile_count(t_coder *coder)` in `coders/src/coder/set_compile_count.c`:
counts one **completed** compile of the coder. The monitor (phase 08) reads
`compile_count` under the coder mutex to decide whether every coder has
compiled at least `number_of_compiles_required` times (subject: the run stops
once everyone *has compiled* that many times), so a compile counts only once
its `time_to_compile` has fully elapsed.

**Contract.** Validate, lock the coder mutex, check `0 <= compile_count <
INT_MAX`, increment, unlock. 0 on success; -1 on NULL input, a counter at
`INT_MAX` or negative (unlock first, field unchanged, never wraps), lock
failure (field unchanged) or unlock failure (field unchanged on a rejected counter; after a successful increment it stays incremented, no rollback).

**Caller rule.** The routine (7.3.1) calls it only after the compile sleep
returned 0 (a compile interrupted by the stop never counts), before releasing
the dongles.

**Preconditions.** The coder mutex is initialised (`init_simulation`) and the
caller does not already hold it.

**Lock order.** The coder mutex is a leaf here: nothing else is locked while it
is held, and it is never held across a log or a sleep.

**Name.** `set_` changes a field (`docs/conventions.md`). Checked: no
`set_compile_count` helper exists in `tests/` or `coders/`.

Orchestration (PLAN.md layers: `coder` module). Close-time documentation: the
`coder/` row of `docs/architecture.md` mentions the completed-compile counter.

**README.** No close-time update (no user-visible change until phase 09).
