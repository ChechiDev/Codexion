## Description

`int set_compile_start(t_coder *coder)` in `coders/src/coder/set_compile_start.c`:
stores the coder's compile start on the simulation clock (ms since
`sim->start_ms`, PLAN.md edf time base). The monitor (phase 08) checks the
burnout deadline (`last_compile_start + time_to_burnout`, subject) from this
field and `build_request` (6.1.2) reads it for the `edf` key, both under the
coder mutex (PLAN.md "Coder thread": a per-coder mutex guards
`last_compile_start` and `compile_count`).

**Contract.** Validate, lock the coder mutex, read the clock, write
`last_compile_start`, unlock. Reading the clock under the lock means a wait on
a contended mutex never publishes a stale (earlier) start, which would shorten
the burnout deadline. 0 on success; -1 on NULL input, clock failure (unlock
first, field unchanged), lock failure (field unchanged) or unlock failure
(field already written, no rollback). The routine (7.3.1) calls it right after
the dongles are taken and before the `is compiling` line; the update and the
log are separate operations, so the stored value is at most the log timestamp.

**Preconditions.** The simulation was built by `init_simulation` (coder mutex
initialised), `start_ms` is set before any coder thread starts and not changed
afterwards, and the caller does not already hold this coder's mutex.

**Lock order.** The coder mutex is a leaf here: nothing else is locked while it
is held, and it is never held across a log or a sleep.

**Name.** `set_` changes a field (`docs/conventions.md`). Checked: no
`set_compile_start` helper exists in `tests/` or `coders/`.

Orchestration (PLAN.md layers: new `coder` module, uses the `time` adapter).
Close-time documentation: new `coder/` row in `docs/architecture.md`.
