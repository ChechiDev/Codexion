## Description

`int wake_dongles(t_sim *sim)` in `coders/src/dongle/wake_dongles.c`: wakes
every thread waiting on any dongle cond, so they can see the stop and leave
(PLAN.md "Monitor thread": on burnout it sets `stop` under a mutex and
broadcasts every dongle cond; phase goal: wake-all on stop).

**Protocol (why locking before the broadcast matters).** The caller first sets
the stop (`set_stopped`, 3.2.2), then calls `wake_dongles`. A waiter (6.3.2,
6.3.4, 6.3.5) checks `is_stopped` while holding its dongle mutex and only then
waits on that dongle's cond, which releases the mutex atomically. Because
`wake_dongles` takes the same mutex before broadcasting, the broadcast happens
either before the waiter checked (it then sees the stop) or after it is
waiting (it is woken): a stop wake-up cannot be lost.

**Callers.** Phase 08 (monitor) after either stop condition; 6.3.4 and 6.3.5
on their fatal path (a failure after a request is queued); phase 09 when a
thread fails to start. None of them may hold a dongle mutex when calling it.

**Return contract.** 0 if every lock, broadcast and unlock succeeded; -1 on
NULL input or any failed step. Best effort: every dongle is visited even after
a failure. It does not change `stopped` or any dongle field: waking is
harmless on a running simulation (waiters re-check and wait again).

**Name.** New verb `wake_` ("wakes threads blocked on a condition"), added to
the closed list in `docs/conventions.md` by a `style/` branch before this
subtask (as PR #8 did for `wait_`, `take_`, `release_`). Checked: no
`wake_dongles` helper exists in `tests/`.

Orchestration (PLAN.md layers: `dongle` module). Close-time documentation: the
`dongle/` row of `docs/architecture.md` mentions the stop wake-up.

**README.** No close-time update (no user-visible change until phase 09).
