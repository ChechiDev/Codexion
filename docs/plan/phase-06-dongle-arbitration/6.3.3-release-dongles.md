## Description

`int release_dongles(t_coder *coder)` in
`coders/src/dongle/release_dongles.c`: gives back the dongles a coder took
(subject: after compiling it returns both dongles to the table; a released
dongle cannot be taken again until `dongle_cooldown` ms have passed).

**Effect.** Under the mutexes of the coder's dongles (lower index first), each
dongle becomes `available = 1` with `released_at = now`, the actual release time:
the simulation clock read after both mutexes are held, in
ms since `start_ms` (same base as `is_dongle_ready`, 6.2.1, which starts the
cooldown from it). Then each dongle's cond is broadcast, so a neighbour waiting
on it re-checks at once (6.3.2: a waiter on the other dongle sees it within its
1 ms slice).

**One coder.** With `first_dongle == second_dongle` (one coder, one dongle) the
single dongle is locked, updated and broadcast once: the same function serves
6.3.4 (two dongles) and 6.3.5 (the single dongle).

**Precondition.** The coder holds the dongles (it took them with 6.3.4 or
6.3.5) and holds no dongle mutex when calling. The function does not check
ownership; the heaps are left alone (requests queued by neighbours stay).

**Return contract.** 0 if every step succeeded; -1 on NULL input, a clock
failure or a lock failure (nothing changed), or a broadcast/unlock failure
(fields already updated, remaining steps still done).

**Name.** `release_` gives back a shared resource (`docs/conventions.md`,
example `release_dongles`). Checked: no `release_dongles` helper exists in
`tests/`.

Orchestration (PLAN.md layers: `dongle` module, uses the `time` adapter). It
comes before `take_dongles` (6.3.4) so the arbiter scenario tests of 6.3.4 and
6.3.5 release through the real function. Close-time documentation: the
`dongle/` row of `docs/architecture.md` mentions release and cooldown start.

**README.** No close-time update (no user-visible change until phase 09).
