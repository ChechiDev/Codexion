## Description

`long get_request_key(t_mode mode, long ticket, long last_compile_start,
int time_to_burnout)` in `coders/src/policy/get_request_key.c`: the priority
key of a dongle request (`t_request.key`, 4.1.1), the single place that knows
the two scheduler policies (subject 6.1.5, PLAN.md "Arbitration keys").

- **fifo:** the key is the arrival `ticket`, so requests are served in arrival
  order. `last_compile_start` and `time_to_burnout` are ignored.
- **edf:** the key is the deadline `last_compile_start + time_to_burnout`
  (subject definition). Ties between equal deadlines go to the earlier ticket
  through `is_request_before` (4.1.1), so the ticket is not part of the key.

**Units.** Under fifo, the key is a dimensionless arrival ticket. Under edf,
`last_compile_start` and the returned deadline are milliseconds elapsed since
the common simulation start. Before a coder's first compilation,
`last_compile_start` is 0; later values record compilation starts on that same
base. Phases 05-08 must use this base consistently for initialization,
arbitration and burnout checks. `time_to_burnout` is a duration in
milliseconds (>= 1).

**Validation.** It returns -1 if `ticket < 0`, if `mode` is neither
`MODE_FIFO` nor `MODE_EDF`, or, under edf, if `last_compile_start < 0`,
`time_to_burnout < 1` (the parser minimum, `get_arg_minimum(2)`) or the sum
does not fit in a `long`. Saturating instead would silently change the order of
requests, so an out-of-range deadline is an error.

**Return contract.** Justified exception to the 0/-1 + out-parameter
convention (same pattern as `get_time_ms`, 3.1.1): an out-parameter would make
five parameters, over the Norm limit of four. Every valid key is `>= 0`, so -1
is unambiguous. Phase 06 callers must check for -1 before constructing or
enqueueing the request; on failure they propagate the error without inserting
an entry into either dongle heap (the comparator of 4.1.1 accepts negative
keys, so it would not catch the sentinel).

Pure core (PLAN.md layers): no pthread, clock, output or allocation. Close-time
documentation: the `policy/` row of `docs/architecture.md` mentions it.

**README.** No close-time update (no user-visible change until phase 09).
