## Description

User decision after 1.2.1 was closed: the scheduling type reads better as a
"mode". In `main.h`:

- `typedef enum e_policy { POLICY_FIFO, POLICY_EDF } t_policy;` becomes
  `typedef enum e_mode { MODE_FIFO, MODE_EDF } t_mode;` (still avoids
  `SCHED_FIFO`, which `<pthread.h>` defines; `MODE_FIFO`/`MODE_EDF` collide with
  nothing in the system headers).
- The `t_config` field `t_policy scheduler;` becomes `t_mode mode;`.
- `main.h` keeps having no system include (review guidance, `docs/architecture.md`).

The subject's command-line argument keeps its name `scheduler` (`fifo` / `edf`)
in every user-facing text; phase 02's parser maps it to `mode`. Nothing else in
`coders/` uses these names yet, so `main.h` is the only production file.

1.2.1 stays as delivered (commit `cde7ce6`, spec and reference doc unchanged):
this subtask supersedes its names.

## Gate step: older oracle compatibility (not an acceptance criterion)

`tests/acceptance/test_1.2.1.c` (sealed, Codex-owned) checks the old names and
would fail to compile once the header is renamed. Before the implementer starts,
as a separate step of this subtask's plan gate:

1. Codex updates `tests/acceptance/test_1.2.1.c` only where it names the old API
   (`t_policy` -> `t_mode`, `POLICY_FIFO`/`POLICY_EDF` -> `MODE_FIFO`/`MODE_EDF`,
   field `scheduler` -> `mode`); every other check of 1.2.1 stays identical.
2. The human re-seals it: `./harness/review_with_codex.sh seal 1.2.1`.

Both tests (`test_1.2.1.c` and `test_1.2.2.c`) are red until the implementer
renames the header, and both must be green at this subtask's code gate.
