## Description

`int run_simulation(t_sim *sim, const t_config *config)` in
`coders/src/lifecycle/run_simulation.c`: runs one whole simulation from a
validated configuration and reports whether it ended normally (0) or because
of an internal error (-1). It is what `main` calls after argument validation
(9.5.2).

**Preconditions.** `config` was validated by `parse_config`; `sim` is
storage owned exclusively by the caller, holds no active simulation, and is
not copied while it holds mutexes; after any return the caller neither
reuses nor cleans it up: on 0 it was already freed (or never initialised,
zero required), on -1 it is either freed or deliberately kept for the
process lifetime, and `main` reports the error and ends the process at once
(9.5.2). The single -1 hides which of the two happened on purpose: the caller
must not act on the storage in either case.

**Storage is the caller's.** `sim` points to storage owned by the caller
(`main`'s stack in 9.5.2), not a local of `run_simulation`. On the
unrecoverable paths (`start_threads` -2, `join_threads` -1) a thread may still
use the simulation, so it must not be freed and its storage must stay valid
until the process ends (9.3.1 contract). With the storage in `main`, it lives
until `main` returns, which ends the process; a local `t_sim` here would expire
on return while a thread could still read it. Keeping the memory on those
paths is a safety choice for a programming error, not a way to meet "no
leaks".

**Zero compiles required** (user decision 2026-11-06, PLAN.md "Edge cases"):
the target is met before anything happens, so the run ends at once with no
thread and no output. This reads subject line 137 ("if every coder compiled
at least this number of times the simulation stops") for the degenerate case;
it is documented for the defense.

**Normal ends.** Target met and burnout are both normal: the run did what the
subject asks. Only `failed` (set by a coder, the monitor or `start_threads`)
or a lifecycle failure turns the result into -1.

**Name.** `run_` is listed for thread routine bodies in
`docs/conventions.md`, whose `run_` row now also lists the one whole-run driver
`run_simulation` as an explicit exception (named in PLAN.md and phase 09 since
the roadmap; conventions row extended 2026-11-07). Checked: no `run_simulation` exists in
`tests/` or `coders/`.
