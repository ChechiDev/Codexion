## Description

`int start_threads(t_sim *sim)` in `coders/src/lifecycle/start_threads.c`:
starts the simulation clock and launches the monitor thread, then one thread
per coder (user decision 2026-11-06: monitor first, no start barrier). On a
failed start it cleans up the threads it created so the caller does not have
to, except in the unrecoverable -2 case.

**Preconditions.** `sim` was built by `init_simulation`; `start_threads` is
called once per simulation, by a single caller, with no thread of this
simulation running yet.

**Return contract.**
- 0: every thread was created successfully (some may already have finished
  by the time it returns); the caller must later wait for them with
  `join_threads(sim, number_of_coders)` (9.4.1).
- -1: the start failed and no thread of this simulation is left running
  (none was created, or every created one was joined). The caller may free
  the simulation. When `sim` is NULL nothing is touched; when the clock read
  fails `sim` is left untouched (`failed` not set: no thread ever existed and
  the caller knows the start failed); when a `pthread_create` failed,
  `set_failed` was called (an attempted mark, with the mutex-failure limits of
  9.1.2).
- -2: the start failed and the recovery join failed (9.3.1): some thread may
  still use the simulation, so the caller must not free, reuse or re-join it
  and must keep its storage valid until the process ends (9.3.1 contract).
  An unrecoverable programming error; keeping the memory in that case is a
  safety choice, not a way to meet "no leaks".

**Why the clock first.** Coders compute burnout and `edf` keys from
`start_ms`, and `last_compile_start = 0` is its relative origin. Writing it
before the first `pthread_create`, and never again, makes it race-free: thread
creation publishes the write to the monitor and to every coder, so their reads
need no mutex. The monitor watches from the first instant (no window without
supervision, advisory point 3 of `progress/advisory_09_breakdown.md`). Coders
created later lose the creation time from their first deadline; the subject
counts time from the start of the simulation, so that is correct; with
normal scheduling creation takes microseconds per thread, but no fixed margin
guarantees it under arbitrary load. That the clock is set before any
creation is code review (an early first log line is scheduling-dependent,
not a reliable oracle).

**Failure paths keep the lifecycle invariant (9.2.3).** Any `pthread_create`
failure is an internal error and marks `failed` (phase 09 task 9.3 goal).
When the monitor cannot be created no thread exists, so nothing is stopped,
woken or joined. When a coder cannot be created, `failed` is marked
**before** the stop, so the monitor's view "every stop except mine comes from
a failure that marks `failed`" holds; then the run is stopped and every
waiter woken, so the created coders and the monitor end, and they are joined.

**Name.** From the `start_` / `join_` row of `docs/conventions.md`. Checked:
no `start_threads` exists in `tests/` or `coders/`.
