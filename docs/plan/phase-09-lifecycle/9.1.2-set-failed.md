## Description

`int set_failed(t_sim *sim)` in `coders/src/state/set_failed.c`: records that
an internal error happened during the run (user decision 2026-11-06: runtime
failures make `main` exit non-zero). It sets `sim->failed = 1` under
`stop_mutex` and returns 0; it returns -1 if locking `stop_mutex` fails
(nothing written) or if unlocking it fails (`failed` already 1). Project
return convention: `docs/conventions.md`.

**Marks, does not stop.** Stopping the run stays the job of `set_stopped`
(3.2.2), and waking the waiters the job of `wake_dongles` (6.3.1). A failing
thread will call, in this order, `set_failed`, then `set_stopped`, then
`wake_dongles`, each tried even if the previous one failed (9.2, 9.3). This
recovery sequence is best effort: after an unlock failure of `stop_mutex`
somewhere, re-acquiring it is not guaranteed to work, so no progress is
promised on that path. Writing `failed` first keeps the error recorded even if
another thread already stopped the run normally (AC3); no joint atomic
transition of both flags is needed, because `failed` is only read after
successful joins of every thread that was created (9.1.1, 9.4.1).

**Why `stop_mutex`.** It already guards the simulation-wide end state
(`stopped`), is short-held and is a leaf for every caller of `set_failed`.
Not taking `log_mutex` keeps `set_failed` usable while another thread holds
the output lock (AC5) and adds no new lock-order edge: the existing order
`log_mutex → stop_mutex` is unchanged.

**Preconditions.** `sim` is a valid pointer to a simulation built by
`init_simulation` (9.1.1 clears `failed`), and the caller does not hold
`stop_mutex`. On success, `set_stopped`, `is_stopped` and `print_burnout`
leave `stop_mutex` unlocked when they return; after one of them reported an
unlock failure, calling `set_failed` is not guaranteed to succeed (see the
best-effort note above).

**Name.** Mirrors `set_stopped` (`set_` + state). Checked: no `set_failed`
exists in `tests/` or `coders/`.

**README.** No update (no user-visible change yet; the exit status is
documented with 9.5.2).
