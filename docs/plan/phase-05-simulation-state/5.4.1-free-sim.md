## Description

**Type.** `t_sim` (minimal since 3.2.1) moves after `t_coder` in the Types
section, because it now holds the arrays, and gains five fields:

    typedef struct s_sim
    {
        t_config         config;        /* validated arguments (phase 02) */
        long             start_ms;      /* 0 until phase 09 starts the threads */
        int              stopped;       /* guarded by stop_mutex */
        long             next_ticket;   /* guarded by ticket_mutex (phase 06) */
        t_dongle         *dongles;      /* config.number_of_coders, or NULL */
        t_coder          *coders;       /* config.number_of_coders, or NULL */
        pthread_mutex_t  stop_mutex;
        pthread_mutex_t  log_mutex;
        pthread_mutex_t  ticket_mutex;
    }   t_sim;

`t_coder.sim` stays `struct s_sim *` (5.3.1). `next_ticket` and
`ticket_mutex` implement the phase 04 invariant: one simulation-wide, strictly
increasing ticket per logical request, synchronized; phase 06 hands them out.
Phase 03 code (`is_stopped`, `set_stopped`, `sleep_ms`, the logger) only
uses `start_ms`, `stopped`, `stop_mutex` and `log_mutex` by name, so it is
unaffected.

**Function.** `int free_sim(t_sim *sim)` in `coders/src/cleanup/free_sim.c`:
the full teardown, reverse of `init_sim` (5.4.2): the coders array
(`free_coders`, 5.3.3), the dongles array (`free_dongles`, 5.2.3), then the
ticket, log and stop mutexes. Each array pointer is reset to NULL after it is
freed.

**NULL arrays are allowed.** An array pointer that is NULL is skipped. This is
what lets `init_sim` (5.4.2) use `free_sim` as its rollback once the three
mutexes are live: it sets both pointers to NULL first, so a failure while
building the dongles or the coders leaves a simulation `free_sim` can tear
down. That is why this subtask comes before `init_sim`.

**Precondition.** The three mutexes are initialised and unlocked; each array
is either NULL or fully initialised with `config.number_of_coders` elements;
every thread has been joined (phase 09). Calling it twice is undefined
behaviour (the mutexes would be destroyed twice).

**Return contract.** 0 if every step succeeded; -1 if `sim` is NULL or any
step failed. Teardown is best effort: a failing step does not skip the next
ones, so nothing leaks. `config`, `start_ms`, `stopped` and `next_ticket` are
left as they are.

Adapter (PLAN.md layers: `init`/`cleanup` own the mutex/cond/alloc lifecycle).
Close-time documentation: the `cleanup/` row of `docs/architecture.md` mentions
it, and the state section describes the full `t_sim`.

**README.** No close-time update (no user-visible change until phase 09).
