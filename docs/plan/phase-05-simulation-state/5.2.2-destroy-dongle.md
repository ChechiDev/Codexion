## Description

`int destroy_dongle(t_dongle *dongle)` in
`coders/src/cleanup/destroy_dongle.c`: releases everything `init_dongle`
(5.2.1) created, in reverse order: the request heap array (`free_heap`, 4.2.2,
which also resets the heap to `NULL`/0/0), the cond, then the mutex.

**Precondition.** `dongle` was fully initialised by `init_dongle` (returned 0)
and not destroyed since; its mutex is unlocked and no thread waits on its cond
or will touch it again (in the simulation: every thread has been joined, phase
09). `init_dongle` rolls back its own failures, so a dongle whose init failed
is never passed here. Calling it twice on the same dongle is undefined
behaviour (POSIX: destroying a destroyed mutex or cond), unlike `free_heap`.

**Return contract.** 0 if every step succeeded; -1 if `dongle` is NULL or a
`pthread_*_destroy` call failed. Teardown is best effort: a failing step does
not skip the next ones, so the heap array is always freed. `available` and
`released_at` are left as they are (meaningless after destruction); a later
`init_dongle` overwrites them.

Adapter (PLAN.md layers: `init`/`cleanup` own the mutex/cond/alloc lifecycle).
Close-time documentation: `docs/architecture.md` gains the `cleanup/` row.
