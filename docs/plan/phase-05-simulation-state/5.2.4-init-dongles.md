## Description

`int init_dongles(t_dongle **out, int n)` in `coders/src/init/init_dongles.c`:
allocates the array of the `n` dongles of the circle (subject: as many dongles
as coders; PLAN.md "Concurrency design") and initialises each one with
`init_dongle` (5.2.1), index 0 first. Index `i` is the dongle that
`get_dongle_pair` (5.1.1) returns for the seats around it.

**Rollback.** If element `i` fails, `init_dongle` has already rolled that
element back, so `init_dongles` hands the `i` live elements and the array to
`free_dongles(array, i)` (5.2.3), the single teardown path, and returns -1.
Nothing stays allocated or initialised after a failure.

**Return contract.** 0 on success, with `*out` pointing to the array. -1 if
`out` is NULL, `n < 1`, the byte size would overflow `size_t`, `malloc` fails,
or any element fails; on -1 `*out` is not written (`docs/conventions.md`).

**Ownership.** On 0 the caller owns the array and every element and releases
them with `free_dongles(*out, n)` (5.2.3), once no thread uses them (phase 09
joins first). `n` comes from `t_config.number_of_coders`, already validated as
`>= 1` and `<= INT_MAX` (phase 02); no upper cap is imposed (PLAN.md "Out":
no cap on `number_of_coders`), so a huge `n` simply fails at `malloc`.

Adapter (PLAN.md layers: `init`/`cleanup` own the mutex/cond/alloc lifecycle).
Close-time documentation: the `init/` row of `docs/architecture.md` mentions it.
