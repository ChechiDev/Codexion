## Description

Test-only verification (no production behaviour change). It checks the PLAN.md
sufficient condition `B >= C + R + N * (C + D) + 10` with the full binary, at
the boundary and above it. As PLAN.md defines it, `R` is `time_to_debug +
time_to_refactor`, so each AC's value is exactly the bound:

| AC | N | C | R | D | `C + R + N * (C + D) + 10` |
|---|---|---|---|---|---|
| AC1 | 6 | 100 | 100 (50 + 50) | 10 | 100 + 100 + 660 + 10 = 870 |
| AC2 | 5 | 200 | 400 (200 + 200) | 0 | 200 + 400 + 1000 + 10 = 1610 |
| AC3 | 4 | 200 | 400 (200 + 200) | 50 | 200 + 400 + 1000 + 10 = 1610 |
| AC4 | 2 | 200 | 400 (200 + 200) | 0 | 200 + 400 + 400 + 10 = 1010 |

The oracles may already pass at the
plan gate (AGENTS.md, test-only verification). They are evidence over finite
scenarios, not the proof, and they rely on the scheduling assumptions PLAN.md
states.

**`N = 6`.** AC1 is a six-coder run at the bound. A full-binary test cannot
establish the ticket order, so no ticket-interleaving claim is made here; the
order itself stays covered by the sealed phase 06 API oracles.
