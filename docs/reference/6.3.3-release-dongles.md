## Releasing a shared resource safely

Two coders can use the same dongle at different times, but a release has more work than changing an availability flag. The dongle must be made visible to future requests, its cooldown must begin at the real release instant, and any thread sleeping on its condition variable must get a chance to re-check eligibility.

For a coder using dongles `a` and `b`, `release_dongles` orders the indices and takes both mutexes in that order. Once both are held, it reads elapsed simulation time and writes that same value to each dongle's `released_at`, while setting `available` to 1. It then broadcasts on both condition variables and unlocks in reverse order.

```text
lock lower index ──> lock higher index ──> read elapsed time
       │                                              │
       └────────────── both protected ────────────────┘
                              │
                 mark available + released_at
                              │
                 broadcast both conditions
                              │
                 unlock higher, then lower
```

The release timestamp is read only after lock acquisition. If a thread waits for a contended mutex, cooldown therefore starts when the dongle can actually be released, not when the function began waiting. The readiness policy can then express the boundary directly: for cooldown `C`, a queued request becomes cooldown-eligible at `released_at + C`.

The min-index lock order is shared with acquisition and waiting code, preventing opposite-order pair locking from forming a cycle. A one-coder simulation maps both hands to the same dongle; the function recognizes this and locks, updates, broadcasts, and unlocks that one object exactly once.

The request heaps are deliberately untouched. Releasing a resource changes availability and timing, while queued requests retain their scheduler keys and tickets. The condition broadcast prompts waiters to re-evaluate those requests under the arbiter's existing rules.

On invalid pointers, invalid dongle indices, lock failure, or clock failure, the operation reports `-1`; validation and clock failures leave dongle fields unchanged, and a second-lock failure releases the first lock. After state is changed, broadcast or unlock errors still produce `-1`, but the remaining notifications and unlocks are attempted so cleanup is not skipped.

<!-- section: planning -->
## How it was planned

The approved spec scopes this orchestration operation to `coders/src/dongle/release_dongles.c`, its public declaration in `coders/main.h`, and the source list in `coders/Makefile`. It depends on the readiness predicate (6.2.1) and bounded wait (6.3.2), and it is placed before acquisition so later arbitration behavior can use the real release path.

Acceptance criteria cover a two-dongle release and timestamp, waking a waiter on each condition, preserving queued requests and cooldown semantics, the one-coder/single-dongle case, invalid inputs, and a release timestamp taken after contention clears. Build, Norm, and failure-path properties are specified as code review checks.

<!-- section: execution -->
## How it was executed

The function separates pointer/index selection, pair unlocking, state updates, and notifications into small helpers. It validates before taking locks, acquires the lower index first, reads elapsed time only after both locks are held, updates both resources with a shared timestamp, broadcasts while their state is protected, then unlocks in reverse order. It reports partial cleanup failures while continuing the remaining cleanup steps. No heap entries, unrelated mutexes, allocations, or output are involved.

The one-dongle path uses pointer identity to avoid a duplicate lock or duplicate state write. The review also added an index range guard so malformed coder seat data cannot select outside the simulation's dongle array.

<!-- section: problems -->
## Problems & resolution

The first implementation wrote the release state twice when a one-coder simulation mapped both hands to the same dongle. Code review identified the duplicate update; the implementation now updates the second dongle only when it differs from the first. The resulting path touches and notifies the single dongle once.
