## Claiming the terminal log line

A burnout log entry marks the point after which ordinary state messages must
stop. `print_burnout` therefore has two connected responsibilities: it claims
the simulation's first stop, then writes the terminal line while ordinary
loggers are still excluded from the output stream.

```text
print_state:   log lock → check stopped → maybe write state line → unlock
print_burnout: log lock → claim stop → write burnout line → unlock
```

The shared `log_mutex` serializes both paths. The burnout operation acquires it
before `stop_mutex`, claims `stopped` while both are held, then releases
`stop_mutex` before output. It retains `log_mutex` through the call to
`print_log_line`, so a state logger either finishes before the burnout line or
observes the committed stop afterwards. The burnout line is therefore the last
accepted log line.

For example, when coder 3 burns out 1204 milliseconds after the run starts:

```text
1204 3 burned out
```

Only one concurrent caller can claim the transition. That call writes the
terminal line; later burnout calls and state loggers return `-1` without
writing. A later `set_stopped` is harmless because the stop is already set.
Once the transition is claimed, it remains committed even if clock, formatting,
output, or unlock work fails. The return value is `0` only when the line and
required unlocks succeed; failures return `-1` and may follow a committed stop
or partial output.

The operation formats and writes through `print_log_line`, which owns the
shared timestamp, byte construction, and single unbuffered write path. This
keeps timestamp and output behavior consistent with ordinary state lines.

<!-- section: planning -->
## How it was planned

The approved spec scopes one log adapter function and three production files:
`print_burnout.c`, its declaration in `main.h`, and its source registration in
the deliverable `Makefile`. The 12 acceptance criteria cover the exact line,
immediate pipe visibility, timestamp bounds, first-stop and repeated-call
behavior, state suppression, races with other burnout and state loggers,
invalid coder and lock failures, write errors, and build integration. The
monitor's burnout detection cadence and the end-to-end 10 ms deadline remain
for later phases.

<!-- section: execution -->
## How it was executed

The implementation holds `log_mutex` for the whole decision and logging
sequence. A small helper claims the first stop under `stop_mutex`; the caller
then invokes `print_log_line` exactly once while still owning the log lock. This
preserves the lock order shared with `print_state`, avoids a second timestamp
and output implementation, and ensures the terminal message follows any state
line already in progress. Mutex results are checked, and only locks acquired by
the call are released.

<!-- section: problems -->
## Problems & resolution

The initial implementation duplicated timestamp, formatting, and writing, and
used helper names outside the project's closed verb list. The work was replanned
after the shared logger declaration and extraction (3.4.5 and 3.4.6); this
implementation was written fresh to use `print_log_line` and the allowed
`set_stopped_once` helper name.
