## Turning a trimmed digit span into an integer

Numeric arguments arrive as strings, so parsing must decide exactly which bytes represent a value and whether that value fits in an `int`. `parse_number` composes the span helper from [[2.1.1-trim-span]] with a digits-only conversion. It accepts surrounding C-locale whitespace because `trim_span` removes it, then requires at least one ASCII digit (`0` through `9`) in the remaining span.

Leading zeroes are fine and do not count against the value limit. For example:

| Input | Result |
|---|---:|
| `"007"` | 7 |
| `"     0007     "` | 7 |
| 30 zeroes followed by `"42"` | 42 |
| `"2147483647"` | `INT_MAX` |

Signs, internal spaces, punctuation, non-ASCII bytes, and an empty span are invalid. The parser also rejects a value above `INT_MAX` without allowing intermediate arithmetic to overflow. Before adding the next digit it checks whether the current value can safely grow by one decimal place:

```text
if value > (INT_MAX - digit) / 10: reject
value = value * 10 + digit
```

The check happens before the multiply and addition. This matters for very long input: wrapping first could turn a huge number into a small, plausible integer. The result is assigned only after every character has passed validation, so failure preserves the caller's output variable.

This primitive checks representation and range only. The later config parser applies each argument's minimum value.

## How it was planned

Subtask 2.1.2 was planned as a pure core helper built on the already approved `trim_span`. Its declared files are [[coders/src/parsing/parse_number.c]], [[coders/main.h]], and [[coders/Makefile]]. Acceptance covers ordinary and boundary values, surrounding whitespace, invalid characters and encodings, overflow at and beyond `INT_MAX`, null pointers, unchanged input and output on failure, and build plus Norm requirements. The plan keeps field-specific minimums in the later config parser, 2.2.3.

<!-- section: execution -->
## How it was executed

The parser obtains one span from `trim_span`, rejects an empty span, and scans its bytes once. It checks each byte against the ASCII digit range before deriving the digit, then applies the pre-arithmetic overflow bound. It holds the accumulated value locally and writes through `out` only after the full span succeeds. This keeps the API deterministic and leaves normalization in one shared helper; no allocation, I/O, or mutation is needed.

## Problems & resolution

The phase review found that the minimum-check cross-reference in the description pointed to the scheduler parser. The plan was corrected to identify 2.2.3, where `parse_config` applies the numeric minimums. No implementation findings remained at the code review gate.
