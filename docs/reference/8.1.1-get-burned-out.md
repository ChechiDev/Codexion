## Checking a coder's burnout deadline

A coder burns out when the simulation clock reaches the deadline for beginning
their next compile. Before the first compile, the reference point is the start
of the simulation. Later, `last_compile_start` records the beginning of the
most recent compile. If `T` is `time_to_burnout`, the deadline is:

```text
deadline = last_compile_start + T
burned   = now >= deadline
```

The comparison includes the deadline itself. With a 300 ms burnout interval,
an elapsed time of 299 ms is still safe, while 300 ms means the coder has
burned out. A coder who has already reached the required number of compiles
can still be reported as burned out; the monitor's separate target check
decides when the simulation is complete.

`get_burned_out` samples the coder's last compile start and the simulation
clock while holding that coder's mutex. This makes the two values describe a
consistent instant: a concurrent compile cannot renew the start between the
state read and the clock read. The monitor can then make a decision from that
snapshot. Once it observes a burnout, the monitor treats it as terminal.

The deadline test avoids adding the two potentially large timestamps. Since
the elapsed simulation time is nonnegative and the configured interval is
positive, it compares `last_compile_start <= now - time_to_burnout`. This also
handles extreme stored timestamps without overflowing. For example, a start
at `LONG_MIN` is overdue, while `LONG_MAX` is not due for any representable
elapsed time.

The function returns 0 and writes 0 or 1 to its output on success. Invalid
pointers, mutex errors, or a clock error return -1, leaving the output
untouched. It does not log: the monitor owns the decision to report a burnout.

<!-- section: planning -->
## How it was planned

Subtask 8.1.1 adds one orchestration function in `coders/src/monitor/`, its
prototype in the Monitor section of `coders/main.h`, and its source entry in
`coders/Makefile`. The acceptance criteria cover the exact deadline boundary,
alternate configured intervals, real clock behavior, a coder who has met the
compile target, extreme timestamps, contention with a compile-start update,
and invalid input. The contract also requires no logging or state mutation.

<!-- section: execution -->
## How it was executed

The implementation validates inputs before attempting synchronization, then
holds only the coder mutex across both reads. It computes the boundary using a
subtraction form that remains safe for extreme start values, unlocks, and only
then publishes the result. This preserves the out-parameter on every error
path and keeps burnout detection separate from logging and monitor policy.
The `monitor/` module is recorded in [[docs/architecture.md]].
