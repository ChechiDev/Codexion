## Coordinating simulation completion

The monitor thread combines two independent facts about the simulation: whether
every coder has completed the configured number of compiles, and whether any
coder has missed its next-compile deadline. The monitor owns the policy that
turns those observations into one terminal outcome.

Each pass checks conditions in a deliberate order:

```text
someone already stopped?   -> leave quietly
all compile targets met?   -> stop and wake dongle waiters
any coder burned out?      -> print one burnout line, then wake waiters
otherwise                 -> check again after at most 1 ms
```

Target completion wins when a scan sees both completion and a missed deadline.
For example, if all four compile counts are `3` for a target of `3`, an overdue
coder does not produce a burnout line. If one count is still `2`, an overdue
coder is reported instead. A target of zero is already met, so the run ends
without waiting for or reporting a deadline.

The loop uses the read-only checks from [[docs/reference/8.1.1-get-burned-out]]
and [[docs/reference/8.1.2-get-target-met]]. It scans coders in index order and
reports the first burned coder. The exact winner among simultaneous deadlines
is intentionally not part of the public oracle, leaving the selection rule
local to a helper if a later defense changes it.

The burnout line is emitted through `print_burnout`, which serializes the log
and commits the stop together. The monitor then broadcasts to every dongle
condition variable so blocked coders can observe the stop. For target completion
and check failures it explicitly sets stop before waking waiters. If another
thread already stopped the run, that thread owns the wake-up and the monitor
leaves without printing. On a failure while handling burnout, it attempts stop
and wake-up even if one step fails, avoiding a live run without a working
monitor.

The cadence keeps detection near the subject's 10 ms burnout reporting budget:
one sleep slice is at most 1 ms, followed by the checks and the serialized
write. This assumes ordinary scheduling and a consumer that keeps output from
blocking on a full pipe.

## How it was planned

Subtask 8.2.1 completes task 8.2 by combining the two monitor queries from
8.1.1 and 8.1.2 in a single orchestration thread routine. The sealed scope adds
`run_monitor` in `coders/src/monitor/run_monitor.c`, its declaration in
`coders/main.h`, and its source entry in `coders/Makefile`. Acceptance criteria
cover deadline timing and line output, simultaneous deadlines, target completion
(including zero and a target reached during the run), target precedence in a
joint scan, external stop, waiter wake-up, NULL, one coder, and output failure.
The phase review had already approved the monitor module and its dependency
chain.

<!-- section: execution -->
## How it was executed

The routine delegates synchronized reads and stop/log operations to their
existing APIs, keeping mutex ownership out of the loop. Static helpers keep
burned-coder selection and the shared stop-and-wake exit policy contained in
the new source. It checks completion before deadlines, uses the first burned
index returned by the selector, and relies on `print_burnout` to make the stop
and line atomic. It sleeps in checked 1 ms slices only while no terminal
condition has been found.

The user chose target-first precedence for a joint observation, consistent with
the subject's completion wording. The lowest-index tie-break is the current
implementation; alternate tie-break policies remain a local defense change and
were not added to the sealed acceptance oracle. The `monitor/` module mapping in
[[docs/architecture.md]] already describes the responsibilities introduced by
this routine, so no architecture change was needed at close.

## Problems & resolution

None during implementation or code review. The plan review recorded the
target-first decision and left tie-break flexibility in the single selection
helper; the code review approved the resulting implementation without requested
changes.
