<!-- section: concept -->
## Put generic text helpers in the utils layer

`trim_span` finds the part of a string between its leading and trailing whitespace. It returns a view: a pointer into the original string plus a length. It does not allocate memory or alter the source text.

For example, trimming `"  42  "` yields a span of length two that points at `"42"`. Parsing can then validate and convert those characters without making a temporary copy. An inner space remains part of the span, so `"4 2"` is still rejected as an invalid number.

This helper has no knowledge of arguments or configuration. Keeping it in `utils/` makes the dependency direction clear: parsing can use generic string utilities, while the utilities do not depend on parsing. Moving its source file preserves the helper's behavior and ownership contract.

## How it was planned

The subtask declares a pure move from `coders/src/parsing/trim_span.c` to `coders/src/utils/trim_span.c`, plus the source path update in `coders/Makefile`. The prototype remains unchanged for the following header organization subtask. AC1 checks trimming through `parse_number`, including all six recognized whitespace characters and rejection of interior whitespace. AC2 covers the build, no relink, and Norm. The earlier 2.1.1 acceptance check was migrated to expect the new Makefile path and resealed as part of the plan gate.

## How it was executed

The helper body was moved without behavioral changes; only its 42 header was refreshed for the new file location. The Makefile now compiles the utility-layer path. Keeping the API stable means callers and the sealed trim contract do not need to change as a result of this move.
