## Driving a simulation from setup to cleanup

`run_simulation` coordinates the lifecycle operations into one call. It
initializes the caller's `t_sim`, starts the monitor and coder threads, joins
them, checks whether any thread recorded a runtime failure, and releases the
initialized resources. It reports only success (`0`) or failure (`-1`); the
later program entry point is responsible for presenting an error to the user.

```text
validate pointers
      |
zero compiles? ── yes ──> return 0 without touching sim
      |
initialize ── failure ──> return -1 (initializer rolled back)
      |
start threads ── -1 ────> free initialized state, return -1
      |             -2 ──> retain state, return -1
      |              0
      v
join all threads ─ failure ─> retain state, return -1
      | success
      v
read failed; always free state ─> 0 only if neither failed nor cleanup failed
```

The startup and join result contracts control whether cleanup is safe:

| Result | State ownership consequence | Driver action |
|---|---|---|
| Initialization fails | Initializer has already rolled back partial setup. | Return `-1`; do not free again. |
| Startup returns `-1` | Startup has recovered all created threads. | Free initialized state, then return `-1`. |
| Startup returns `-2` | A recovery join failed; a thread may still use `sim`. | Return `-1` and keep caller storage valid until process exit. |
| Normal join fails | Completion of every thread is not known. | Return `-1` without reading or freeing shared state. |
| All joins succeed | No thread can access the simulation anymore. | Read `failed`, always attempt cleanup, then combine the results. |

The caller owns the storage, so it can keep that storage alive even on an
unrecoverable join failure. The public `-1` deliberately does not reveal
whether resources were freed; the caller must report the error and end the
process without reusing or cleaning the storage. A successful run can end
because every coder met its target or because the monitor logged a burnout;
both are normal simulation outcomes.

## How it was planned

The approved orchestration subtask adds `run_simulation` in
`[[coders/src/lifecycle/run_simulation.c]]`, its public declaration in
`[[coders/main.h]]`, and the source-list entry in `[[coders/Makefile]]`.
Acceptance criteria cover a zero-target no-op, target completion, burnout,
one-coder behavior, runtime output failure, and invalid pointers. The code
review check assigns cleanup ordering and the unsafe-thread lifetime cases to
source inspection, since ordinary inputs cannot force those lifecycle failures.
The caller keeps exclusive ownership of `t_sim`; the later entry-point task
provides storage that remains valid until process exit.

<!-- section: execution -->
## How it was executed

The driver uses one private helper for the post-startup join path. It reads
`failed` only after every join succeeds, when no thread can still update it,
and stores the cleanup result separately so cleanup always runs even when a
thread reported failure. Initialization failure is already rolled back by
`init_simulation`; a failed recovery join or normal join leaves the caller's
storage intact. A zero compile target returns before initialization, keeping
the degenerate case free of threads, output, and persistent state changes.
