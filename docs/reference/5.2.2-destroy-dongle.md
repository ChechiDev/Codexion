## Releasing a dongle's owned resources

A successfully initialized dongle owns three resources: a request heap array, a condition variable, and a mutex. Destruction releases them in the reverse order from initialization:

```text
init:     mutex → condition variable → heap array
 destroy: heap array → condition variable → mutex
```

The heap is released through `free_heap`, which also resets its public state. For example, after successful destruction its fields are `items == NULL`, `size == 0`, and `capacity == 0`. The synchronization objects have no corresponding reusable field state; after they are destroyed, the dongle must not be used until `init_dongle` initializes it again.

Teardown is best effort. If destroying the condition variable fails, the mutex destroy is still attempted; if either pthread destroy operation reports an error, the function returns `-1`. The heap release still occurs, so an error in a later cleanup step does not strand its allocation. `NULL` is rejected with `-1` before any access.

The caller must ensure the dongle is fully initialized, its mutex is unlocked, and no thread is waiting on its condition variable or will use it again. In the simulation this means joining the threads before teardown. Destroying a live synchronization object, or destroying it twice, violates that precondition. After a valid destruction, the same storage can be initialized again; initialization overwrites the ordinary state fields.

<!-- section: planning -->
## How it was planned

Subtask 5.2.2 pairs with `init_dongle` and declares one cleanup adapter, its public prototype, and the build entry. Acceptance criteria cover an empty heap, queued requests and modified ordinary state, exercised synchronization objects, reinitialization and reuse, repeated teardown as specified by the oracle, and NULL rejection. Pthread destroy failure paths are checked by code review because forcing a failure portably would require invalid synchronization-object use.

<!-- section: execution -->
## How it was executed

The adapter delegates heap ownership to `free_heap`, then attempts condition-variable and mutex destruction in reverse initialization order. It accumulates a failure result instead of returning early, preserving best-effort cleanup. It does not acquire the mutex: callers own the lifecycle boundary and must stop all users before teardown.

The `cleanup/` row in [[docs/architecture.md]] records that resource teardown belongs to the adapter layer and depends on the core heap API.
