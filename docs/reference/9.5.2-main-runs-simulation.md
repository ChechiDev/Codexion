## Connecting validated input to a complete run

`main` is the boundary between command-line input and the simulation lifecycle.
It first checks the argument count and values. Only valid input reaches
`run_simulation`, which owns initialization, thread coordination, and cleanup.
The entry point translates the driver's result into a process status:

| Status | Meaning | Output |
|---|---|---|
| 0 | The run ended normally: the compile target was reached, a coder burned out, or zero compiles were required. | Simulation events, if any, go to stdout. |
| 1 (`EXIT_USAGE`) | The argument count or a value is invalid. | Argument errors and usage reminder go to stderr; no simulation starts. |
| 2 (`EXIT_RUNTIME`) | A valid run encountered an internal failure. | `Error: simulation failed` goes to stderr. |

For example, a successful run can produce state lines and finish with status 0:

```text
0 1 has taken a dongle
0 1 is compiling
200 1 is debugging
400 1 is refactoring
```

If writing a state line fails, the same valid invocation ends with status 2 and
the fixed diagnostic on stderr. This keeps runtime failures distinct from
input errors and keeps diagnostics out of the simulation log.

The simulation structure lives on `main`'s stack. This matters because the
lifecycle driver's unrecoverable thread paths can return while a thread may
still reference that structure. `main` reports the failure and returns
immediately, ending the process without reusing or freeing storage that may
still be in use. The ordinary success path returns only after the driver has
joined its threads and cleaned up.

## How it was planned

The interface-layer subtask declares `[[coders/main.c]]` and
`[[coders/main.h]]` for the entry point and `EXIT_RUNTIME` macro, plus
`[[README.md]]` for the user-facing exit-status description. It depends on
`[[docs/plan/phase-09-lifecycle/9.4.1-run-simulation.md]]` and
`[[docs/plan/phase-09-lifecycle/9.5.1-print-run-error.md]]`. Seven binary-level
acceptance criteria cover target completion, burnout, one coder, a zero-target
fast path, runtime output failure, unchanged argument errors, and leak-free
full runs. Source-specific storage and delegation constraints are checked at
the code gate.

<!-- section: execution -->
## How it was executed

After existing validation succeeds, `main` creates its `t_sim` locally and
passes it to `run_simulation`. A zero result maps to status 0. A failure calls
the CLI-owned `print_run_error` and returns `EXIT_RUNTIME` immediately, leaving
the lifecycle driver's ownership and cleanup decisions intact. Validation
continues to use the existing usage path and status. The README now describes
these outcomes alongside the command-line behavior.

<!-- section: problems -->
## Problems & resolution

The existing unit test expected valid arguments to produce no stdout because
`main` previously stopped after parsing. Once the entry point started the
simulation, that expectation no longer matched the intended behavior. The
unit assertion was updated to require simulation output for valid input; the
argument-error assertions remain unchanged.
