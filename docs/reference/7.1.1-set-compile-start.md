## Recording the start of a compile

The simulation needs one shared timestamp for each coder's most recent compile start. The EDF scheduler uses it to calculate a request deadline, and the monitor will use it to determine when the coder burns out. The value is elapsed milliseconds from the simulation's start, so a stored value of `500` means the compile started half a second into the run.

`set_compile_start` updates that timestamp while holding the coder's own mutex. It reads the clock only after acquiring the mutex. If it read the clock first and then waited for a contended lock, it could publish a start time from before the coder actually began compiling, shortening the available burnout interval.

```text
lock coder.mutex
    start = get_elapsed_ms(sim.start_ms)
    coder.last_compile_start = start
unlock coder.mutex
```

For example, if the simulation began at `10000 ms` and the clock reads `10525 ms`, the stored value is `525`. A later EDF deadline is then `525 + time_to_burnout`. The later coder routine calls this operation after acquiring dongles and before writing the `is compiling` log line, so the timestamp and log are separate events.

On success the function returns `0`. Invalid pointers, a lock failure, or a clock failure return `-1` without changing the field. A clock failure releases the lock before returning. If unlocking fails after the assignment, the function reports `-1`; the stored timestamp is not rolled back.

<!-- section: planning -->
## How it was planned

The approved scope adds `set_compile_start` in the orchestration layer, declares it in the Coder section of `coders/main.h`, and registers its source in `coders/Makefile`. Acceptance criteria cover a timestamp bounded by clock reads around the call, overwrite, clamping of a future simulation start, blocking under mutex contention, and invalid inputs. Clock and pthread failure paths are checked by source review because they cannot be forced reliably in the black-box tests.

<!-- section: execution -->
## How it was executed

The function validates the coder and its simulation, locks only that coder's mutex, obtains elapsed time through the existing time adapter, and stores the result under the same lock. Reading the clock inside the critical section is the key contract: contention cannot make the published time stale. The operation does not change the compile count or other coder/simulation state, and does not log, sleep, allocate, or hold the mutex across another operation.
