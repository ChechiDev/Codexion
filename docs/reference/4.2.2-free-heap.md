## Releasing a heap and returning it to the empty state

A heap owns a dynamically allocated array of `t_request` slots. `size` says
how many leading slots currently hold requests, while `capacity` records the
array's fixed length. Releasing the heap means releasing that one allocation
and resetting all three fields so the same struct clearly owns no storage:

```text
before: { items: allocated array, size: 3, capacity: 4 }
free_heap(&heap)
after:  { items: NULL,            size: 0, capacity: 0 }
```

The request values are stored directly in the array, so there are no
per-request allocations to release. A zeroed heap already has the empty state;
calling `free_heap` on it is safe because C permits `free(NULL)`. Resetting the
fields after release also makes cleanup repeatable: another call sees NULL
storage and leaves the heap empty.

The contract relies on ownership: a non-NULL heap must be zeroed, previously
released, or initialized successfully by [[docs/reference/4.2.1-init-heap.md]].
Passing an uninitialized struct with garbage pointer bits is invalid because
those bits do not identify storage owned by the heap. Once released, the struct
can be initialized again with `init_heap`; cleanup should happen after users of
the heap have stopped accessing it.

<!-- section: planning -->
## How it was planned

Subtask 4.2.2 declares one core teardown function in
[[coders/src/heap/free_heap.c]], its public prototype in [[coders/main.h]], and
build registration in [[coders/Makefile]]. Its six acceptance criteria cover
freeing empty, partially occupied and full heaps; repeated and NULL calls;
reuse after release; and deliverable build integration. The spec separately
requires a single release followed by resetting all fields, with no other
allocation, locking, clock, output or global dependency.

<!-- section: execution -->
## How it was executed

The function treats NULL as an absent cleanup target. For a valid heap, it
releases the owned array once and publishes the empty state by clearing the
pointer, size and capacity. This gives callers one cleanup operation that can
be used on partially filled heaps and safely repeated on zeroed or already
released heaps. The heap row in [[docs/architecture.md]] already describes
`free_heap` as part of core heap storage management, so no architecture change
was needed at close.
