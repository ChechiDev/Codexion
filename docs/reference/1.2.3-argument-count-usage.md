## Rejecting an incomplete command line

The command line is the boundary between the user and the program. Before it
can parse values or start work, the entry point checks that all eight required
arguments are present. In C, `argc` includes the executable name, so eight
user arguments means `argc == 9`.

When the count is wrong, the program prints a usage reminder to standard error
and exits with status 1. Standard output stays empty. The message gives the
argument order and the two accepted scheduler spellings:

```text
$ ./coders/codexion
Usage: ./codexion number_of_coders time_to_burnout time_to_compile time_to_debug time_to_refactor number_of_compiles_required dongle_cooldown scheduler
  scheduler is either fifo or edf
```

The same response applies to too few or too many arguments. This early check
keeps malformed invocations away from later parsing and simulation work. It
does not validate the values when the count is correct; that belongs to the
argument parsing phase.

<!-- section: planning -->
## How it was planned

Subtask 1.2.3 scopes one CLI behavior: reject any count other than eight
arguments, report usage on stderr, and return status 1. The declared files are
`coders/main.c`, `coders/main.h`, and `README.md`. Acceptance criteria cover no,
too few, and too many arguments; the usage text and order; Norm; and README run
instructions with a matching output example.

<!-- section: execution -->
## How it was executed

`main` compares `argc` with 9 before doing further work. Its `print_usage`
helper uses `fprintf(stderr, ...)`, while the header exposes only the helper
prototype and `EXIT_USAGE` constant. Keeping `<stdio.h>` in `main.c` avoids
adding an I/O dependency to the shared header. The README documents all eight
arguments and shows the actual wrong-count output. A unit test also captures
both output streams to check the entry-point contract.
