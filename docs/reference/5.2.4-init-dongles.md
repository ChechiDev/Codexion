## Building the dongle array as one owned resource

A simulation has one dongle per coder. Each dongle carries its own mutex, condition variable, and two-slot request heap, so array initialization must create independent per-element resources rather than copy or share them.

The operation has a clear ownership boundary:

```text
caller provides out
        │
        ▼
allocate n slots ── initialize 0 ── initialize 1 ── ... ── initialize n-1
        │                   │              │                       │
        └────────────── publish *out only after every element succeeds ──────┘
```

On success, `*out` owns the array and each initialized dongle. The caller later passes that pointer and the full count to `free_dongles`. For example, a four-coder simulation has four separate heaps, each starting empty with capacity two, and four unlocked mutexes.

If initialization fails at element `k`, `init_dongle` has already undone any resources belonging to that element. The array initializer therefore frees only the live prefix `[0, k)` through `free_dongles(array, k)`. At `k == 0`, this still frees the outer allocation without attempting to destroy an uninitialized element. The caller's output pointer remains unchanged on every failure.

The array allocation size is checked before multiplication so an extreme count cannot wrap the byte size. A count that passes that arithmetic check can still fail allocation; there is no arbitrary upper limit imposed here.

<!-- section: planning -->
## How it was planned

The approved subtask adds one init adapter function and declares its source, `main.h` prototype, and `coders/Makefile` entry. Acceptance criteria cover initial state for four elements, counts one and 200, independent mutexes and heaps, a heap push isolated to one element, and invalid arguments preserving the output pointer. Allocation and element-initialization failures are reviewed from the rollback code because the harness has no portable deterministic fault injection. The plan depends on `init_dongle` (5.2.1) and `free_dongles` (5.2.3), making the latter the common rollback and teardown path.

<!-- section: execution -->
## How it was executed

The initializer validates the output pointer and count, checks the allocation size bound, allocates once, and calls `init_dongle` in ascending index order. It delegates resource ownership to the per-dongle initializer and delegates partial-prefix teardown to `free_dongles`, avoiding a second implementation of cleanup rules. The result pointer is assigned only after the full loop succeeds.

This keeps array orchestration in the `init/` adapter while the core heap remains unaware of allocation of simulation state. The `init/` row in [[docs/architecture.md]] already describes this responsibility, so no architecture change was needed.
