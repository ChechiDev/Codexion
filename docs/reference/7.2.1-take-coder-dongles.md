## Acquiring dongles and making acquisition visible

A coder may need two adjacent dongles to compile. When there is only one coder, both of its dongle references identify the same resource, so it must acquire that dongle once. The coder orchestration operation selects the matching acquisition API and then writes one `has taken a dongle` line for each distinct resource.

```text
pair:   take_dongles -> log first -> log second -> report taken
single: take_single_dongle -> log once -> report taken
```

The log lines are the public indication that ownership has been acquired. Therefore the caller's `taken` result is published as `1` only after every required line succeeds. If acquisition sees a stop, the function reports success with `taken == 0` and does not log. If a log fails, it attempts one release. A successful release followed by an observed stop is treated as normal stopping (`0`, `taken == 0`); without an observed stop the operation returns `-1`. This stop precedence handles the fact that the logger uses `-1` both for a deliberately dropped stop-time line and for an output failure.

The caller's output is a commit-style result: it changes only on a `0` return. Invalid input, acquisition failure, and an unrecovered log failure preserve its prior value. The underlying pair and single acquisition functions own their own partial-failure behavior, so this wrapper does not retry or guess which locks/resources they may still own after a `-1`.

<!-- section: planning -->
## How it was planned

Task 7.2 adds the coder layer between resource arbitration and the coder thread loop. The approved spec declares `take_coder_dongles.c`, the Coder section of `coders/main.h`, and the source entry in `coders/Makefile`. Its six acceptance criteria cover pair and one-coder acquisition, a pre-existing stop, log failure and release, invalid inputs, and ticket exhaustion. The plan assigns deterministic public behavior to acceptance tests and lock or stop interleavings that cannot be forced reliably to source review.

<!-- section: execution -->
## How it was executed

The wrapper validates the coder, output pointer, and simulation before calling a dependency. It chooses `take_single_dongle` when both coder dongle pointers match and otherwise calls `take_dongles`, passing a local result so a dependency failure cannot overwrite the caller's sentinel. A zero acquisition result is copied to the caller and returns without logging. A successful acquisition is followed by one or two `print_state` calls. On the first logging error, the wrapper calls `release_dongles` once; it then applies the release result and stop-precedence rule. No mutex is held by this wrapper across logging, and stop/wake policy remains with its caller.

<!-- section: problems -->
## Problems & resolution

The advisory review found that the underlying pair and single acquisition APIs can return `-1` after some internal failure paths have changed resource state, so the wrapper could not promise that failure always leaves everything untouched. The spec was clarified to defer those paths to the acquisition APIs, return directly without retry or extra cleanup, and preserve only the caller's `taken` output. The same review clarified that a failed log needs one release attempt and that a stop observed after a successful release takes precedence over the ambiguous logger error. These contracts were approved before implementation; no code-gate findings remain.
