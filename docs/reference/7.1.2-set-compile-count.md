## Counting completed compiles safely

`compile_count` records how many full compile intervals a coder has completed. The distinction matters when the simulation stops during a compile: an interrupted interval is not a completed compile and must not advance the count. The coder routine calls this operation only after the compile wait finishes successfully, and does so before releasing the coder's dongles.

The field is shared with the monitor and other threads. The coder's mutex makes each increment an indivisible read-check-write operation:

```text
lock coder.mutex
    if compile_count < 0 or compile_count == INT_MAX:
        unlock coder.mutex
        return -1
    compile_count = compile_count + 1
unlock coder.mutex
return 0
```

For example, if the count is `41`, one successful call leaves it at `42`. At `INT_MAX - 1`, a call reaches `INT_MAX`; another call is rejected without wraparound. A negative value is treated as corrupted state and is also rejected without modification. Concurrent callers therefore serialize instead of losing increments.

A NULL coder or lock failure returns `-1` without changing the count. A rejected count is left unchanged and the mutex is released. If the final unlock itself fails after a successful increment, the function reports `-1` but does not roll the completed increment back.

<!-- section: planning -->
## How it was planned

The approved scope adds one orchestration function in `coders/src/coder/set_compile_count.c`, declares it in the Coder section of `coders/main.h`, and adds the source to `coders/Makefile`. Acceptance criteria cover repeated increments on one coder, upper and corrupted lower bounds, concurrent callers, blocking under mutex contention, and NULL input. Lock and unlock failures are covered by source review because they cannot be forced deterministically. The spec also requires the architecture note to describe the coder module's compile-state responsibilities; no README update is needed because this subtask adds no user-visible behavior.

<!-- section: execution -->
## How it was executed

The function checks NULL before locking, then checks the range and increments while holding only the target coder's mutex. Keeping the bound check and update in the same critical section prevents both overflow and lost updates. Rejected values are unlocked before returning, and an unlock failure after a valid increment is reported without rollback. The operation does not acquire simulation or dongle locks, log, sleep, allocate, or modify other coder state.
