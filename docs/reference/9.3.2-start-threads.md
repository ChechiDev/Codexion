## Starting a simulation's threads

Starting a simulation establishes its shared time origin and creates the
monitor and coder threads that use the initialized `t_sim`. The startup order
is deliberate: set `start_ms`, create the monitor, then create coders in
configuration order. The monitor watches from the first instant, and each
thread created after the clock write observes the same origin.

```text
read clock ──> publish start_ms ──> create monitor ──> create coder 0 … N-1
```

The operation reports whether ownership can safely proceed:

| Result | Meaning | Caller action |
|---:|---|---|
| `0` | Every thread was created; some may already have finished. | Join all coders and the monitor. |
| `-1` | Startup failed, and no thread remains unjoined. | The simulation may be freed. |
| `-2` | Startup failed and recovery joining failed. | Keep the simulation storage alive until process exit; do not read, reuse, free, or join it again. |

If the clock read fails, startup returns `-1` before changing the simulation.
If thread creation fails, it records the failure. A monitor creation failure
has no thread to stop or join. A coder creation failure marks failure, requests
stop, wakes dongle waiters, and joins the monitor and the coders already
created. Each recovery action is attempted independently; if the recovery join
fails, `-2` makes the unsafe lifetime explicit.

The caller must invoke startup once, on a simulation built by
`init_simulation`, before any simulation thread is running. A successful
startup does not join, free, or print anything. `run_simulation` owns those
later lifecycle decisions.

<!-- section: planning -->
## How it was planned

The subtask adds `start_threads` to lifecycle orchestration, with its source,
public declaration, and Makefile entry as the three declared deliverable
files. Acceptance criteria cover a normal target run, the one-coder burnout
case, opportunistic thread-creation failure and recovery, and NULL input.
Failure paths that cannot be triggered portably are explicit source-review
checks. The plan fixes the clock-before-create order, monitor-first policy,
return contract, and caller obligations after a failed recovery join.

<!-- section: execution -->
## How it was executed

The implementation reads the clock into a local value before assigning
`sim->start_ms`, then creates the monitor and delegates coder creation to a
small helper. A separate recovery helper marks failure, stops and wakes the
simulation, and passes the exact count of created coders to `join_threads`.
This lets the same join API serve both partial startup and normal completion.
Successful startup leaves joining to its caller; it does not assume ownership
of the simulation storage.
