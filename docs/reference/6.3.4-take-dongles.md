## Acquiring a pair as one operation

A coder needs two dongles to compile. Acquiring them one at a time creates a hold-and-wait problem: two coders could each hold one dongle while waiting forever for the other. `take_dongles` treats the pair as one request. It queues the same request in both dongle heaps, then takes both resources only when that request is at the head of both queues and both dongles are available and past cooldown.

```text
build request (no dongle locks)
          |
lock lower index, then higher index
          |
push identical request into both heaps
          |
   +------+----------------+
   |                       |
stopped?            ready at both?
   |                       |
unlock, return 0     pop both, mark both unavailable,
                     unlock, return taken=1
                           |
                     otherwise wait, retry
```

For example, if a request is at the head of dongle 2's heap but not dongle 3's, the coder cannot take either resource. This head-of-both rule preserves the scheduler's FIFO or EDF order across the pair. The lower-index-first lock order prevents pair-lock cycles, and the check plus both state changes happen within one critical section.

The call returns `0` with `*taken = 1` when it acquired the pair, or `0` with `*taken = 0` when the simulation is stopped. It returns `-1` for invalid input or a fatal operation failure, leaving `*taken` untouched and releasing every mutex it still holds. Once a request is queued, a fatal failure cannot safely remove it from the heaps; the function therefore stops the simulation and wakes dongle waiters so the run can shut down instead of leaving a stale queue head blocking progress.

Every unsuccessful iteration waits on the first dongle's condition variable for a bounded slice, with the wait helper temporarily releasing and restoring the pair locks. This lets the thread re-check stop, queue priority, availability, and cooldown without busy-waiting. The stop check is coordinated with the dongle condition wait, so the stop-and-wake protocol cannot lose a wake-up.

<!-- section: planning -->
## How it was planned

The approved spec places pair acquisition in `coders/src/dongle/take_dongles.c`, adds its declaration to `coders/main.h`, and registers the source in `coders/Makefile`. It depends on request creation, readiness, wake, wait, and release operations. Acceptance criteria cover free-pair acquisition, head-of-both ordering, FIFO versus EDF priority, cooldown, stop behavior, concurrent progress evidence, and invalid inputs. Failure paths that cannot be forced deterministically are code-review checks.

<!-- section: execution -->
## How it was executed

The implementation validates the coder and dongle pair before mutation, builds its request before locking, then locks both dongles in index order and pushes the same request into both heaps. A small set of helpers separates validation, queueing, per-iteration arbitration, and pair cleanup. Success pops both queue entries and marks both dongles unavailable while both mutexes are held. A stopped simulation exits without taking either dongle. Queued-request failures release held locks, set stop, and broadcast wake-ups; failures before queueing simply clean up and return an error. The caller handles logging after acquisition returns.

The corrected progress oracle checks its shared ownership slots only after all worker threads have joined. This keeps that evidence race-free while preserving the criterion's purpose of checking neighboring coders' mutual exclusion and completion.

<!-- section: problems -->
## Problems & resolution

The first code review found static helper names outside the project's approved verb list. They were renamed to `get_dongles`, `release_pair`, `push_requests`, and `take_pair`. The acceptance progress test also read shared owner slots while other workers could still update them; its assertion was moved after all joins, then the plan was re-sealed and the corrected oracle's ThreadSanitizer run was recorded clean.
