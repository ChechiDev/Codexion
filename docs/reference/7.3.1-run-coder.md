## Coordinating one coder's thread

`run_coder` is the thread routine for one coder. It coordinates operations that already have their own contracts: `take_coder_dongles` acquires the required resource and logs each distinct dongle, the compile-state functions update synchronized fields, `print_state` writes the visible cycle, and the sleep and release functions handle timing and resource ownership.

For a coder with a pair of dongles, each complete cycle is:

```text
take and log both dongles
record compile start
log "is compiling"
wait time_to_compile
count the completed compile
release dongles
log "is debugging"   -> wait time_to_debug
log "is refactoring" -> wait time_to_refactor
check stop state
```

The order carries the important boundaries. A compile count advances only after its full wait returns successfully, and the pair is released before debugging begins. A stop during compile therefore leaves the count unchanged and triggers cleanup for the still-held pair. The stop check after refactoring also ends a run whose waits all have zero duration.

One coder has a single dongle, represented by its first and second dongle pointers referring to the same object. That path takes and logs the resource once, then repeatedly performs positive, interruptible sleeps. It does not compile or print a burnout message; the later monitor owns burnout policy and its user-visible line. When the run stops, the routine releases the single dongle and returns.

The function always returns `NULL`, as required by `pthread_create`. A normal stop returns through the cycle or acquisition checks. If a dependency reports `-1`, the routine makes at most one release attempt for dongles it still records as held, then calls `set_stopped` and `wake_dongles` so other threads can leave. It clears its ownership flag before attempting release, since a failed release is not safe to retry. The lifecycle phase can later add a way to distinguish this failure exit from a normal stop.

## How it was planned

The approved subtask adds one orchestration entry point in `coders/src/coder/run_coder.c`, its Coder-section declaration in `coders/main.h`, and the source registration in `coders/Makefile`. Acceptance criteria cover ordered cycles and timestamps, shared-pair spacing and state, the one-coder wait, prompt stopping, interrupted compile accounting, pre-stopped input, dependency-failure cleanup, and invalid pointers. The spec assigns clock, lock/unlock, setter, release, and exact stop-check failure paths that cannot be forced reliably to code review. No README behavior change is planned before lifecycle integration in phase 09.

<!-- section: execution -->
## How it was executed

The routine keeps ownership in a local flag and divides the work into small helpers for the cycle, rest interval, single-coder wait, and common failure exit. It does not hold a mutex of its own across a log or sleep; those dependencies own their synchronization. Both the pair and single-coder paths clear the local ownership state before release, ensuring there is no retry after an ambiguous release failure. A `-1` from stop-aware logging or sleeping follows the same cleanup route as a real dependency error, which is safe because stop and wake operations are idempotent on an already stopped simulation.

<!-- section: problems -->
## Problems & resolution

The advisory reviews refined the failure contract before implementation. Because a dependency may fail after changing resource state, the routine only attempts release when it still owns the resource according to its local flag and never retries that attempt. The spec also makes wake-up unconditional after the stop attempt and defines compile counts as completed waits only. These decisions keep cleanup bounded and allow other coder threads to exit; no code-gate findings remained.
