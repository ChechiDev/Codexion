## Separate a normal monitor stop from an error

The monitor scans coder state and can end the simulation for different reasons. Reaching the compile target and reporting a burnout are expected outcomes. A failed check, interrupted wait, or failed burnout log means the run did not complete normally. Keeping these outcomes distinct lets the lifecycle preserve failures for the caller without changing the established monitor scan policy.

| Monitor outcome | Report | Stop and wake | Failure state |
|---|---|---|---|
| Target reached, including a target of zero | No line | Stop and wake dongle waiters | Remains clear unless stop or wake fails |
| Coder burnout | One burnout line | Wake dongle waiters | Remains clear unless logging or wake fails |
| Dependency or logging error | No successful burnout line is promised | Attempt stop and wake | Mark failed first |
| Someone else already stopped the run | No line | No additional action | Leave unchanged |

The error path preserves the original cause before cleanup:

```text
check or log fails
        ↓
   set failed
        ↓
   set stopped
        ↓
   wake dongle waiters
```

Each cleanup action is attempted even if an earlier one fails. In the production lifecycle, a normal stop comes from this single monitor; other stops are part of failure handling. That invariant allows a failed burnout report to be treated as an error, including when the print helper reports that a stop has already occurred. This is a best-effort contract: `is_stopped` also represents a mutex error as stopped, so the monitor cannot promise to detect every underlying synchronization failure.

<!-- section: planning -->
## How it was planned

The approved scope declares only [[coders/src/monitor/run_monitor.c]] for modification. Acceptance criteria cover clean target completion, zero required compiles, a logged burnout, a failed burnout write, an external silent stop, unlocked state after exit, and waiter wake-up on the error path. The sealed 8.2.1 acceptance test remains the regression oracle for scan behavior, latency, and normal wake-up. Dependency failures that ordinary inputs cannot force are assigned to source review. No public identifier or README update was planned.

<!-- section: execution -->
## How it was executed

The scan retains its prior order and passes a classified result to one exit helper. The helper handles silent exit, clean stop, burnout, and error separately. It records failure before stop and wake on an error, and treats failures while stopping a clean target completion or waking after burnout as runtime failures. This keeps state classification at the monitor boundary while reusing the existing synchronized state, log, and wake APIs. The implementation adds no public API or allocation.
