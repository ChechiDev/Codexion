## Reserving storage for a binary min-heap

A binary heap is a complete binary tree laid out in a flat array. For an item
at index `i`, its children are at `2i + 1` and `2i + 2`; the parent of a
non-root item is `(i - 1) / 2`. Because the tree is complete, this layout needs
no pointers between nodes. The minimum request stays at `items[0]`, as defined
by the request ordering in [[docs/reference/4.1.1-is-request-before.md]].

```text
                 items[0]
              /            \
         items[1]          items[2]
         /     \            /     \
     items[3] items[4]  items[5] items[6]

array: [0, 1, 2, 3, 4, 5, 6]
```

`init_heap` reserves a fixed number of request slots and starts the heap empty.
For example, capacity 4 reserves four independently writable `t_request`
objects, while `size` remains zero:

```text
before: { items: unused, size: 0, capacity: 0 }
init_heap(&heap, 4) -> 0
after:  { items: allocated array, size: 0, capacity: 4 }
```

The allocated slot contents are unspecified. Later heap operations may read
only the occupied prefix `[0, size)`, so a slot must be written before it
becomes occupied. The array belongs to the caller and is released by
[[docs/plan/phase-04-priority-queue/4.2.2-free-heap|`free_heap`]]. A non-NULL
heap must be writable and must not already own a live allocation; initialization
does not inspect prior fields, and reinitializing a live heap would lose its
pointer.

The function validates the pointer and positive capacity, checks that the
element count can be multiplied by `sizeof(t_request)` without overflowing
`size_t`, and then allocates. It writes the heap fields only after allocation
succeeds. Thus every failure returns `-1` with the caller's structure
unchanged; success returns `0` with `size == 0` and the requested capacity.

## How it was planned

Subtask 4.2.1 declares `coders/src/heap/init_heap.c`, the `t_heap` type and
prototype in [[coders/main.h]], and build registration in
[[coders/Makefile]]. Acceptance criteria cover successful capacities 1, 2 and
1000; writable slots; preservation of sentinel-filled heap storage on invalid
capacities; NULL input; independent allocations; and build, exported symbol and
Norm integration. The code review check additionally requires overflow-safe
size calculation, no field writes before successful allocation, and a single
allocation with no I/O, locking, clock or global state.

<!-- section: execution -->
## How it was executed

The implementation computes the allocation size only after checking the
capacity bounds, keeping the multiplication in `size_t`. It stores the result
of `malloc` in a temporary pointer and returns immediately on failure. Only
then does it publish the pointer, empty size and fixed capacity together. This
ordering implements the shared out-parameter rule: callers never observe a
partially initialized heap after an error.

The new `heap/` row in [[docs/architecture.md]] places storage management in
the core layer. The heap's ordering relationship to `policy/` is explicit,
while the heap operations remain responsible for maintaining the array
invariant.
