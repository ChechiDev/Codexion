## Reading the EDF viability boundary

The viability boundary is a sufficient condition for EDF to avoid burnout under the scheduling assumptions laid out in [[docs/plan/PLAN.md]]. It gives a conservative way to choose a burnout limit when each coder needs time to compile, debug, refactor, and wait for service around the shared dongles.

Let `C` be compile time, `D` the dongle cooldown, `R` the sum of debugging and refactoring time, and `N` the number of coders. With 10 ms reserved for scheduling slack, the sufficient condition is:

```text
N >= 2
B >= C + R + N * (C + D) + 10
```

Here `B` is the burnout limit. The `N >= 2` condition matters because a single coder has only one dongle and cannot compile with the required pair. For multiple coders, the bound accounts for the coder's own work before requesting again, service for up to `N` epochs, cooldown, and the slack margin. EDF prioritizes the closest deadline; the heap and acquisition rules described in the plan support the service bound.

For example, with six coders, `C = 100`, `D = 10`, and `R = 50 + 50 = 100`:

```text
minimum sufficient B = 100 + 100 + 6 * (100 + 10) + 10 = 870 ms
```

The full-binary scenario uses `870` ms, so it sits exactly at the stated boundary. Other boundary examples vary coder count, compile time, debugging/refactoring time, and cooldown:

| Coders `N` | `C` | `R` | `D` | Boundary `B` |
|---:|---:|---:|---:|---:|
| 6 | 100 | 100 | 10 | 870 ms |
| 5 | 200 | 400 | 0 | 1,610 ms |
| 4 | 200 | 400 | 50 | 1,610 ms |
| 2 | 200 | 400 | 0 | 1,010 ms |

A separate run at `N = 6`, `B = 1,200` is above the bound and checks that each coder continues to compile. These runs check observable outcomes of the compiled program: successful exit, no burnout message, and the requested compile count for every coder. The log oracle also checks that captured output contains only complete, ordered log lines and that stderr is empty.

Finite runs are evidence for these scenarios, not the proof of the guarantee. The guarantee is the service-bound argument in [[docs/plan/PLAN.md]]. Parameters below the sufficient bound may still work in practice, but this note and these scenarios do not claim they are guaranteed.

<!-- section: planning -->
## How it was planned

The sealed spec declares this as test-only verification with an empty production `files:` list. Its acceptance criteria run the full binary in four exact-bound cases, one above-bound case, and validate all resulting logs. The six-coder boundary case checks another table size; exact FIFO/EDF ticket ordering remains covered by the phase 06 API oracles. The acceptance scenarios were chosen directly from `C + R + N * (C + D) + 10` in [[docs/plan/phase-10-hardening-and-readme/10.2.1-viability-boundary|the subtask spec]].

<!-- section: execution -->
## How it was executed

The work added acceptance coverage only; production behavior and public interfaces did not change. The oracle launches the compiled binary for each scenario, checks its exit result, absence of burnout, and per-coder compile counts, then checks captured output byte-for-byte for embedded NULs before validating complete, non-decreasing log timestamps. It requires stderr to be empty. This byte-range check ensures malformed bytes after a NUL cannot be hidden by string parsing.

The code review is `APPROVED`. The supplied implementation report records clean Valgrind and ThreadSanitizer runs for the acceptance binary. The supplied outside-sandbox `make check` exited 0, including the repository checks and acceptance suite.

<!-- section: problems -->
## Problems & resolution

The first code review found that the log-format oracle stopped at an embedded NUL, potentially ignoring later malformed bytes. The acceptance oracle was corrected to validate the full captured byte range and reject embedded NULs; the plan was resealed and the subsequent code review approved the fix. No production change or acceptance-criteria change was needed.
