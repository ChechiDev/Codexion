## Ordering requests by policy key and arrival

A priority queue needs one rule for deciding which request comes first. Codexion
uses the same comparator for both schedulers: compare the request's `key`, then
use its arrival `ticket` to break ties. The comparator answers a strict question:
does request `a` precede request `b`?

| `a` | `b` | Result | Reason |
|---|---|---:|---|
| `{key: 5, ticket: 9}` | `{key: 6, ticket: 1}` | 1 | Smaller key wins, regardless of ticket. |
| `{key: 7, ticket: 2}` | `{key: 7, ticket: 3}` | 1 | Equal keys use the earlier ticket. |
| `{key: 7, ticket: 3}` | `{key: 7, ticket: 3}` | 0 | An item does not precede an equivalent item. |

```text
compare a.key with b.key
  if different: smaller key comes first
  if equal:     smaller ticket comes first
```

Under FIFO, the policy key is the arrival ticket, so requests are served in
arrival order. Under EDF, the key is the requester's deadline; equal deadlines
still resolve in arrival order. The `coder` field identifies the requester but
does not affect priority. Each logical request receives one unique ticket, and
its two dongle-queue copies therefore compare as equivalent.

Relational comparisons avoid overflow: subtracting `LONG_MIN` from `LONG_MAX`
would not be safe, but testing which value is smaller works over the full `long`
range. A null pointer produces 0 defensively; queue callers are expected to
compare initialized, non-null requests.

<!-- section: planning -->
## How it was planned

Subtask 4.1.1 defines the request type and its strict `(key, ticket)` ordering
as pure core behavior. The declared production files were
[[coders/src/policy/is_request_before.c]], [[coders/main.h]], and
[[coders/Makefile]]. Its acceptance criteria cover key order, tie-breaking,
strictness, independence from `coder`, extreme values, total-order properties,
null inputs, read-only arguments, and build/Norm integration. Key computation
and heap storage/operations remain in later subtasks.

<!-- section: execution -->
## How it was executed

The comparator checks the two fields directly and returns immediately when the
keys differ. It consults the ticket only for equal keys. This keeps policy
ordering centralized and usable by later heap and arbitration code without
adding clock, locking, allocation, or output dependencies. The request type is
declared in the shared header, and the source is registered in the deliverable
Makefile. The architecture map now identifies `policy/` as pure core logic.
