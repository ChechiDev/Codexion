<!-- section: concept -->
## Reading the minimum request without removing it

A min-heap keeps its earliest request at index `0`. `get_head_request` copies
that root into caller-owned output storage; it does not pop the request or
otherwise change the heap. The operation is useful when a scheduler needs to
inspect a candidate before deciding whether it can proceed.

For example, after inserting these requests, the minimum is the `(3, 0)` item
because the heap orders by key and then by arrival ticket:

```text
Heap array: [ (3, 0), (3, 2), (8, 3), (5, 1) ]
                         |
get_head_request          v
Output:                    (3, 0)
Heap array afterward:     [ (3, 0), (3, 2), (8, 3), (5, 1) ]
```

The returned struct is a value copy. Changing it cannot change the stored
request. A NULL heap, NULL output pointer, or empty heap returns `-1`; in those
cases the output is left untouched. The caller provides synchronization when
other threads may access the heap. In later arbitration code, the dongle mutex
protects the read and the caller checks both heap heads before removing either
request.

<!-- section: planning -->
## How it was planned

The approved spec adds one pure core function and declares its source,
`coders/main.h` prototype, and `coders/Makefile` entry. Acceptance criteria cover
copying a single head and successive minima, proving that the heap is unchanged,
empty and invalid calls, copy independence, and build and Norm integration.
The review check separately requires validation before output writes and no
heap traversal, allocation, locking, clock, output, or global state.

<!-- section: execution -->
## How it was executed

The implementation validates both pointers and `heap->size` before assigning
the root value to the caller's output. Keeping this operation as a direct copy
means ordering stays the responsibility of the heap's existing comparator and
push/pop operations. The API accepts a `const t_heap *` to express that it
observes storage only; its caller owns any required lock.
