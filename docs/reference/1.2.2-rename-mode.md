<!-- section: concept -->
## Naming the scheduling choice

The configuration stores the scheduling choice as a `t_mode` value in the
`mode` field. Its two enum constants represent the supported arbitration
choices: `MODE_FIFO` means requests are served in arrival order, while
`MODE_EDF` means they are ordered by their earliest burnout deadline.

```c
t_config config;

config.number_of_coders = 4;
config.time_to_burnout = 800;
config.mode = MODE_EDF;
```

This says the simulation has four coders, an 800 ms burnout limit, and uses
earliest-deadline-first arbitration. The command-line argument remains named
`scheduler` and accepts `fifo` or `edf`; parsing will translate that external
word into the internal `mode` value. Keeping those names separate lets the
configuration describe what the value is while preserving the subject's CLI.

<!-- section: planning -->
## How it was planned

The approved subtask changes the configuration API in one declared file,
`[[coders/main.h]]`. Acceptance criteria require a readable `mode` field of
type `t_mode`, distinct `MODE_FIFO` and `MODE_EDF` values, compile failures for
the superseded names, and a clean Norm run. The argument name `scheduler`
remains part of the user-facing interface.

<!-- section: execution -->
## How it was executed

The enum type and tag were renamed to `t_mode` and `e_mode`; the enum constants
became `MODE_FIFO` and `MODE_EDF`; and the struct member became `mode`. Removing
the old declarations makes stale callers fail at compile time, so the rename is
enforced by the C interface rather than maintained through compatibility
aliases. No system include or runtime behavior was added. The acceptance oracle
also updates the earlier configuration checks to use the new contract.
