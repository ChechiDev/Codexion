## Validate at the program boundary

The entry point is the boundary between command-line text and the rest of the
program. It first checks that the caller supplied all eight required values.
With the correct count, it asks the configuration parser to validate them.
The parser fills one flag per position and returns the number of invalid
arguments. The entry point walks positions 1 through 8, prints each set
position's diagnostic, then prints usage once and exits with status 1. This
preserves argument order in a multi-error report:

```text
Error: time_to_burnout must be an integer from 1 to 2147483647
Error: time_to_compile must be an integer from 0 to 2147483647
Error: scheduler must be fifo or edf
Usage: ./codexion number_of_coders time_to_burnout time_to_compile time_to_debug time_to_refactor number_of_compiles_required dongle_cooldown scheduler
  scheduler is either fifo or edf
```

If the count is wrong, there is no position-specific error to report, so the
entry point prints usage only. If all values are valid, it returns 0. At this
stage, valid input does not start the simulation; a later phase supplies that
work. Validation happens before allocation or thread startup, so this path has
no resources to release.

<!-- section: planning -->
## How it was planned

The approved spec declares [[coders/main.c]] for entry-point validation and
[[README.md]] for the close-stage explanation of accepted values and a real
multi-error run. Its acceptance criteria cover individual and combined invalid
values, successful input, wrong argument counts, invalid-path memory safety,
and Norm. The implementation reuses the parser's per-position flags and the
CLI's position-specific diagnostics rather than duplicating parsing or message
rules in `main`.

<!-- section: execution -->
## How it was executed

`main` retains the exact-count guard, then calls `parse_config` with its local
configuration object and stack flag array. A small static helper scans the
flags in ascending position order and delegates each error line to
`print_arg_error`. `main`
prints usage once after that scan and returns `EXIT_USAGE`. The successful path
returns 0 for now. This keeps `main` as the wiring layer while parsing policy
stays in the core and user-facing text stays in the CLI module.

## Problems & resolution

After validation was added, the unit fixture for the exact-argument-count case
still supplied placeholder strings, which were now correctly rejected. The
fixture was changed to use a valid configuration so it continues to exercise
the argument-count behavior itself.
