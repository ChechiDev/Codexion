## Turning coder state into an arbitration request

Before a coder can wait in the dongle heaps, it needs one request value that both heaps can compare consistently. `build_request` combines two independent pieces: a simulation-wide ticket identifies when the request arrived, and the configured policy computes its primary key. The request also carries the coder's one-based id.

For FIFO, the ticket itself is the key. For EDF, the key is the coder's previous compile start plus the configured time to burnout. The ticket remains attached in both modes; it breaks equal EDF deadlines and gives the logical request one identity across both dongles.

```text
coder state --read under coder mutex--> last_compile_start
                                      \
ticket counter --take_ticket-----------> request { key, ticket, coder }
                                      /
config mode + burnout --policy key-----
```

Example with a burnout time of 800 ms:

| Mode | Coder state | Ticket | Request key | Request |
|---|---:|---:|---:|---|
| FIFO | any valid start | 0 | 0 | `(key=0, ticket=0, coder=1)` |
| EDF | `last_compile_start = 1500` | 1 | 2300 | `(key=2300, ticket=1, coder=4)` |

The function reads `last_compile_start` while holding only that coder's mutex, then releases it before taking the simulation ticket. This matters because ticket allocation has its own mutex: keeping the locks separate avoids introducing a lock-order dependency. It does not lock dongles or queue anything; the caller receives a complete value and later inserts the same request into each relevant heap.

The output is assembled locally and copied to the caller only after every step succeeds. Invalid pointers, lock failures, exhausted tickets, or an invalid/overflowing EDF key therefore leave the caller's output unchanged. A ticket can be consumed before key calculation fails; tickets need to increase strictly, so a gap does not compromise ordering.

<!-- section: planning -->
## How it was planned

The approved scope adds one orchestration function in `src/dongle/`, its declaration in a new Dongle section of `main.h`, and its source in the Makefile. The dependency on 6.1.1 supplies synchronized tickets; 4.1.2 supplies the pure FIFO/EDF key calculation. Acceptance criteria cover sequential values in both modes, no queue or coder-state mutation, overflow and exhaustion with output preservation, concurrent unique tickets, and NULL inputs. Lock and unlock failure handling is checked by source review.

<!-- section: execution -->
## How it was executed

The function validates its inputs, copies the coder's prior compile start under the coder mutex, releases that mutex, obtains a ticket, and asks `get_request_key` to apply the configured policy. It fills a local request first and publishes it only on success. This keeps synchronization in the state adapter, key rules in the pure policy module, and request assembly at the orchestration boundary. No dongle mutex is held and no heap is modified here.

<!-- section: problems -->
## Problems & resolution

The unit fixture initially needed explicit mutex destruction before reinitialization and at exit. That lifecycle was corrected in the fixture; the implementation report records the sequential checks as clean afterward. The helper name was also changed from `read_last_start` to `get_last_start` to match the project's allowed verb conventions.
