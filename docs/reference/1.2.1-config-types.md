## Configuration data and scheduling policy

The configuration is the typed result that later argument parsing will fill
and the simulation will read. Keeping the seven numeric settings together in
`t_config` gives the program one value to validate, pass into initialization,
and inspect while running. Each number is an `int`, matching the parser's
planned `INT_MAX` bound.

The final field, `scheduler`, has type `t_policy`. This enum makes the two
supported scheduling choices explicit and distinct:

| Value | Meaning |
|---|---|
| `POLICY_FIFO` | Handle requests in arrival order. |
| `POLICY_EDF` | Order requests by their earliest deadline. |

A caller can construct and read the configuration directly:

```c
t_config config;

config.number_of_coders = 4;
config.time_to_burnout = 800;
config.scheduler = POLICY_EDF;
```

Here the configuration describes four coders, an 800 ms burnout limit, and
the EDF policy. The other timing and compile-count fields are populated by the
same parsing step. The header has an include guard so including it from more
than one place, or twice in one translation unit, does not redeclare its types.
It needs no system headers because these data types depend only on C built-in
types.

<!-- section: planning -->
## How it was planned

The approved scope is the shared configuration contract and the build
dependency that keeps consumers synchronized with it. The declared files are
`[[coders/main.h]]` for the include guard, policy enum, and configuration
struct, and `[[coders/Makefile]]` for making object files depend on `main.h`.
Acceptance criteria cover all eight fields and their types, distinct policy
values, safe repeated inclusion under the required compiler flags, recompilation
when the header changes, and a clean Norm run.

<!-- section: execution -->
## How it was executed

The types are defined in the shared header without platform includes or
functions. This keeps the configuration contract usable by the parser and
simulation while keeping it independent of I/O. The Makefile's pattern rule
depends on `main.h`, so an edit to a shared type recompiles each object that
uses the rule; unchanged inputs still preserve the existing no-relink behavior.
