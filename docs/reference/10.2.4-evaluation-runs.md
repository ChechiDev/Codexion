## Preparing repeatable evaluation scenarios

Evaluation checks need to exercise both the delivered program and the tools reviewers may use around it. This subtask extends the root development `Makefile` scenario list, which is consumed by `make memcheck` and `make tsan`; it does not change the deliverable under `coders/`.

The acceptance oracle checks properties visible in the binary and object files: undefined symbols against the subject's allowed-function list, file-scope data symbols against the no-globals rule, one impossible-run burnout, invalid-input output, and Valgrind exit behavior. In the Valgrind case, the test distinguishes the target program's expected status from Valgrind's configured error status (`42`) and from a failed launch. This avoids treating an unstarted tool as a successful memory check.

The additional Memcheck and ThreadSanitizer scenarios are:

| Scenario | Purpose |
|---|---|
| `5 800 200 200 200 3 0 edf` | Exercise a multi-coder EDF run with the requested compile target. |
| `6 870 100 50 50 3 10 edf` | Exercise the six-coder EDF run at the sufficient viability boundary described in [[docs/plan/PLAN.md]]. |

These finite checks provide evidence for the listed cases; they do not establish a guarantee for parameters below the sufficient boundary. The startup offset is a scheduling heuristic, so empirical below-bound runs can still burn out under machine load.

<!-- section: planning -->
## How it was planned

The sealed spec declares test-only verification and names only the root [[Makefile]] in `files:`. Its acceptance criteria cover allowed symbols, absence of file-scope globals, an impossible run, invalid input, and real Valgrind execution. The code-review check requires adding the two scenarios above while retaining existing entries, then recording Memcheck and ThreadSanitizer results.

<!-- section: execution -->
## How it was executed

The root `SCENARIOS` list gained the two EDF entries and kept the existing scenarios. The acceptance oracle exercises the compiled program and its object symbols; Memcheck and ThreadSanitizer run the configured scenario list independently. The implementation report records `make memcheck` and `make tsan` both exiting 0, alongside the requested repeated empirical runs.

The empirical runs recorded burnout counts of 1/10 for `5 800 200 200 200 3 0 edf`, `4 610 200 200 200 3 0 edf`, and `4 410 200 200 0 3 0 edf`; the `4 800` and `5 650` cases had 0/10. The user accepted these below-bound burnouts as empirical scheduling outcomes, with the startup offset not guaranteed. They do not change the acceptance criteria or the sufficient-bound claim.

<!-- section: problems -->
## Problems & resolution

The verification sequence was interrupted twice before its implementation report was written; the scenario edit was retained, verification was completed, and the report now records the results. The first nested Valgrind attempt against the acceptance oracle returned 134: the oracle itself starts Valgrind, and Valgrind does not supervise that nested run cleanly. The required memory check was therefore run directly against the configured binary scenarios with `make memcheck`, which exited 0. Repeated empirical tests also showed the accepted below-bound burnouts described above; the user chose to document and accept them rather than investigate them as failures of the sufficient-bound guarantee.
