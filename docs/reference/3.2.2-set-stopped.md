## Making the stop transition visible atomically

The stop flag controls whether simulation work may continue, while the log
mutex also guards the decision to print an ordinary state line. A writer that
changes only `stopped` under `stop_mutex` could race with a logger that already
decided to print. `set_stopped` therefore takes the same outer lock as the
logger before taking the flag lock:

```text
set_stopped                         state logger
    |                                   |
    | lock(log_mutex)                   |
    | lock(stop_mutex)                  |
    | stopped = 1                       |
    | unlock(stop_mutex)                |
    | unlock(log_mutex)                 |
    |                                   |
```

This gives ordinary output a clear boundary: a line already serialized under
`log_mutex` completes before the transition, and a later logger sees the stop
and emits nothing. The operation is idempotent; setting an already-set flag is
still a successful stop request.

| Result | Meaning |
|---:|---|
| `0` | The flag is set and both unlocks succeeded. |
| `-1` | A lock or unlock operation failed. If failure occurs after the assignment, the flag remains set. |

If acquiring `stop_mutex` fails, `set_stopped` attempts to release
`log_mutex` and leaves the flag alone. After changing the flag it attempts
both unlocks in reverse order, even if the first unlock fails. Callers treat
any `-1` as a fatal synchronization error because an unlock failure may leave
a mutex held. The function does not print or wake waiting threads; notification
belongs to the later lifecycle and resource coordination work.

<!-- section: planning -->
## How it was planned

The approved scope adds one state adapter, its public declaration, and its
deliverable build entry. Acceptance criteria cover the running-to-stopped
transition, repeated calls, mutex release, both lock-failure postconditions,
silent operation, and build/export/Norm integration. A source review check
fixes the lock order as `log_mutex` then `stop_mutex`, with both post-transition
unlock attempts required.

<!-- section: execution -->
## How it was executed

The setter uses the shared lock order that the serialized logger will use, so
the stop transition and ordinary output cannot cross. It changes only the
flag while holding both locks, then checks each unlock independently rather
than allowing one failure to skip the other. The existing `is_stopped` reader
continues to use `stop_mutex` alone, and this writer never calls it while
already holding that mutex.
