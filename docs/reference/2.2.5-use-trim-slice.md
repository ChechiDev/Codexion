## Reusing a non-owning slice in number parsing

`parse_number` accepts a string view after removing whitespace at its edges, then interprets the remaining bytes as a non-negative decimal integer. A `t_slice` carries a pointer and a length into the original string, so the parser can inspect only the trimmed range without copying or changing the caller's input.

For example, trimming `"  0042\t"` produces a view of `"0042"`, which parses to `42`. Trimming `"4 2"` leaves the internal space in the view, so the digits-only check rejects it. An empty view is invalid, and overflow is rejected before arithmetic would exceed `INT_MAX`. The output value is assigned only after the whole view is valid.

This subtask changes which shared view API the parser consumes. The parsing rules remain the same; the `trim_slice` helper provides the same trimmed range through `t_slice`.

<!-- section: planning -->
## How it was planned

The approved scope is a structural refactor with no behavior change. Its sole declared file is [[coders/src/parsing/parse_number.c]], where the local `t_span` and `trim_span` call are replaced by `t_slice` and `trim_slice`. Regression criteria preserve the existing numeric contract, cover all six whitespace characters, and require a successful build and clean Norm result.

<!-- section: execution -->
## How it was executed

The parser now obtains a `t_slice` from the shared utility and reads its pointer and length during the existing validation loop. Keeping the view non-owning avoids allocation and preserves the input. Digit validation, overflow handling, and delayed assignment to the output remain unchanged. This completes the caller migration started when `trim_slice` was introduced, allowing the old span API to be removed in a later subtask.
