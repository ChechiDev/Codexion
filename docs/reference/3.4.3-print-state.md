## Serializing ordinary state lines

`print_state` is the adapter boundary between simulation events and the
subject's text log. A coder identifies an event with one of four states; the
logger combines that state with the coder number and elapsed milliseconds to
produce one line, such as:

```text
1204 3 is compiling
```

The state enum deliberately excludes `burned out`. That message ends the
simulation and has a separate operation so claiming the stop and printing its
terminal line can be one coordinated action.

The logger uses two mutexes for different jobs:

| Mutex | Protects | Held while writing? |
|---|---|---|
| `log_mutex` | Output order and the decision to accept a line | Yes |
| `stop_mutex` | The shared `stopped` flag | No |

The lock order is `log_mutex` then `stop_mutex`. While holding the log lock,
the function checks the stop flag, releases its mutex, reads the elapsed time,
builds the line in a local buffer, and makes one `write(1, ...)` call. The stop
mutex is not held during output, so a stop-state query does not wait for a slow
writer. The log mutex remains held so another logger cannot pass the stop
check and print after the stop or interleave with this line.

```text
print_state
    │
    ├─ reject an unknown state
    └─ lock log_mutex
         ├─ lock stop_mutex → read stopped → unlock stop_mutex
         ├─ if running: get elapsed time → build bytes → write once
         └─ unlock log_mutex
```

The buffer is at most `LOG_LINE_MAX` (64) bytes. A successful return means the
single write accepted the complete line and the log mutex was unlocked. Any
rejection or failure returns `-1`. Before the write, failures emit no bytes;
a short or failed write can have emitted a partial line, and an unlock failure
can happen after output. There are no retries, because the contract is one
unbuffered write per line. This makes completed output immediately visible to
pipe readers and serializes concurrent logger calls.

<!-- section: planning -->
## How it was planned

The approved spec scopes this adapter to `print_state`, its `t_state` enum and
prototype in the single header, and its build registration. Its ten acceptance
criteria cover exact event text, immediate pipe visibility, elapsed timestamps,
stopped and invalid input, parallel ordering, stop races, mutex failures, write
errors, and the built symbol. The plan reuses the elapsed clock and stop state
from earlier subtasks and `build_log_line` from 3.4.2.

<!-- section: execution -->
## How it was executed

The implementation maps each enum value to the subject's exact wording, then
serializes the acceptance check and output through `log_mutex`. It reads the
timestamp only after entering that serialized region, which keeps timestamps
non-decreasing in output order unless the wall clock moves backwards. The
existing core formatter handles decimal conversion and line bounds; this
adapter owns only the local buffer and the I/O operation. Each mutex result is
checked, and the function only releases locks it acquired.
