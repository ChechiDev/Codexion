## Checking the simulation through its log

The log is the public trace of a concurrent simulation. A useful black-box check reads the whole trace as an ordered sequence of events and asks whether that sequence could represent the required behavior. It does not need to know which mutex or queue implementation produced it.

Each line has a timestamp, coder ID, and state. From those events, the oracle can check local rules (two dongle takes before a compile and the compile/debug/refactor cycle) as well as rules between coders (neighbor exclusion and alternating service in the two-coder case). For example, a valid cycle has this shape:

```text
12 2 has taken a dongle
12 2 has taken a dongle
12 2 is compiling
112 2 is debugging
212 2 is refactoring
```

The state sequence is a compact trace, while timestamps let the test check ordering and timing constraints. Since release events are not logged, a cooldown assertion uses the compile start plus compile duration as a conservative lower bound for release, then adds the configured cooldown. Timing slack only widens the specified log upper bound in CI; it does not redefine the subject's burnout limit.

| Acceptance | Observable invariant |
|---|---|
| AC1 | Complete, serialized lines; valid IDs and states; non-decreasing timestamps |
| AC2–AC3 | Two takes per compile and the required per-coder state cycle |
| AC4–AC5 | Neighbor compile exclusion and shared-dongle cooldown |
| AC6 | Alternating compile events for two coders under FIFO and EDF |
| AC7–AC8 | One final burnout in the burnout scenario; successful target completion without burnout |

The log cannot reveal request arrival time, so it cannot prove the exact FIFO or EDF queue order. Those policies remain covered by the phase 06 API-level oracles; these checks focus on what the full program makes visible.

<!-- section: execution -->
## How it was executed

The oracle launches the configured binary, captures stdout and stderr into bounded buffers, parses the complete stdout byte range, and builds an event list for the AC checks. It rejects embedded NUL bytes and validates the parsed ID while it is still a `long`, before converting it to `int`. These checks keep malformed trailing output and integer wraparound from appearing valid after parsing.

Implementation verification ran the acceptance suite, Valgrind, and ThreadSanitizer against the test binary, including a separately built TSan child binary. No product code needed changing. The supplied close check also completed successfully outside the sandbox.

<!-- section: problems -->
## Problems & resolution

The first code review found that the AC1 parser narrowed the parsed ID before checking its range, allowing an oversized number to wrap to a valid-looking ID. The oracle was corrected to range-check the `long` first, then re-sealed through the plan gate and approved on re-review. No production behavior or acceptance criteria changed.
