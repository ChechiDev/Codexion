## Reuse one decimal digit rule

`parse_number` reads a trimmed slice and accepts it only when every character
is a decimal digit and its value fits in an `int`. The meaning of “digit” is
defined by the shared `is_digit` utility: exactly the characters from `'0'`
through `'9'`.

For example:

| Input character | `is_digit` result | Parser effect |
|---|---:|---|
| `'0'` or `'9'` | 1 | accepted as a digit |
| `'/'` or `':'` | 0 | rejected at the range boundaries |
| `'+'`, `'-'`, `'a'`, or space | 0 | rejected |

Once a character is known to be a digit, the parser derives its numeric value
by subtracting `'0'`. It checks the accumulated value against `INT_MAX` before
each multiply and addition. Thus leading zeroes remain valid, `INT_MAX` is
accepted, and a larger value is rejected without overflowing the intermediate
integer. The output pointer is written only after the complete slice succeeds,
so invalid text leaves the caller's value unchanged.

```text
trim_slice -> inspect each byte with is_digit -> check range -> assign on success
```

This small refactor gives the parser and other callers one shared definition
of decimal digits. It does not change trimming, accepted input, overflow
handling, or the parser's failure contract.

<!-- section: planning -->
## How it was planned

The approved spec declares a structural refactor with no behavior change and
one production file, [[coders/src/parsing/parse_number.c]]. The only intended
change is replacing the handwritten digit range condition with `is_digit`;
trimming, overflow protection, and output-on-success behavior stay as in
2.1.2/2.2.5. The acceptance criteria preserve that contract, exercise the
digit boundaries, and retain build and Norm coverage. The code review check
requires the parser to call the helper and contain no handwritten range test.

<!-- section: execution -->
## How it was executed

The scan now delegates the yes/no character classification to `is_digit`,
then keeps its existing conversion and pre-arithmetic overflow check. This
preserves the separation between recognizing a character and accumulating a
number. The parser remains a pure core function, and no extra allocation,
copy, I/O, or mutation is introduced.

<!-- section: problems -->
## Problems & resolution

The initial plan review identified that a public-API-only test cannot detect a
behavior-preserving helper substitution. The spec was explicitly classified
as a structural refactor: regression acceptance tests preserve public behavior,
while source inspection at the code review gate verifies use of `is_digit`.
