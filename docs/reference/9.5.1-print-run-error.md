<!-- section: concept -->
## Reporting a failed simulation run

A runtime failure is different from invalid command-line input. The arguments
may be valid and the simulation may have started, but an internal operation
such as thread creation, synchronized state access, logging, or cleanup can
still fail. `print_run_error` gives the entry point one stable message for that
class of failure:

```text
Error: simulation failed
```

The message goes to stderr while simulation state lines remain on stdout. That
keeps the diagnostic separate from the run log and leaves `main` responsible
for deciding when the failure occurred and which exit status to return. The
CLI function takes no simulation pointer, so it does not need to inspect or
change shared state.

| Stream | Purpose |
|---|---|
| stdout | Serialized simulation events |
| stderr | This fixed runtime failure diagnostic |

The fixed wording describes the outcome without exposing internal details that
are not useful for a user of the program. If called more than once, the
function emits one complete line for each call.

<!-- section: planning -->
## How it was planned

The approved interface-layer subtask declares three production files:
`[[coders/src/cli/print_run_error.c]]` for the implementation,
`[[coders/main.h]]` for its public prototype, and `[[coders/Makefile]]` for the
source list. Its two acceptance criteria require the exact stderr line with no
stdout output, then exactly two ordered copies when called twice. The later
entry-point subtask uses this diagnostic when `run_simulation` reports failure.

<!-- section: execution -->
## How it was executed

The CLI function writes the fixed line with `fprintf(stderr, ...)`. It accepts
no arguments, reads no simulation state, allocates no memory, and owns no
mutable global data. Keeping the message in `cli/` follows the project boundary
that assigns user-facing output to that module; lifecycle orchestration can
report an error result without choosing its presentation.
