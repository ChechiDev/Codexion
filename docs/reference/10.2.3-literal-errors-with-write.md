## Literal output and compiler-generated calls

The allowed-function list applies to the executable that is delivered, including calls introduced by the compiler. A fixed string passed to `fprintf` can be optimized into a call to `fwrite`; that makes source-level inspection alone insufficient to establish that the binary avoids a disallowed function.

For these fixed messages, `write` sends the known bytes directly to file descriptor 2 (standard error), and `strlen` supplies their length. For example, the scheduler error remains the same byte sequence:

```text
Error: scheduler must be fifo or edf
```

The argument errors for positions 1 through 7 contain a formatted position value, so they remain on the formatted-output path. Only the literal scheduler message changes. Keeping that boundary preserves the messages while removing the compiler-generated `fwrite` reference from the binary.

<!-- section: planning -->
## How it was planned

The approved production scope names three CLI files: `[[coders/src/cli/print_usage.c]]`, `[[coders/src/cli/print_run_error.c]]`, and `[[coders/src/cli/print_arg_error.c]]`. Acceptance criteria check forbidden undefined symbols, exact output bytes and streams, unchanged argument-error messages, and the closed-stderr exit path. The code review check also requires preserving the formatted numeric errors and public `void` signatures.

<!-- section: execution -->
## How it was executed

Each fixed message now uses one `write` call with `strlen` for its byte count. The return value is checked for a negative result to satisfy the compiler's warn-unused-result setting; the functions still return `void`, so a failed output operation does not change their contract. The numeric-position messages continue to use `fprintf`.

The implementation report records acceptance checks, the undefined-symbol inspection, and Valgrind and ThreadSanitizer runs. Valgrind's child process could not write diagnostics when the acceptance case deliberately closed stderr; directing Valgrind output to a log file allowed the closed-stderr scenario to run and reported no memory errors. The supplied outside-sandbox close check exited successfully.

<!-- section: problems -->
## Problems & resolution

Valgrind could not supervise the child in the closed-stderr acceptance case when its own diagnostics shared the closed descriptor. Sending Valgrind diagnostics to a per-process log file resolved the tooling issue without changing the product or the oracle.
