## Giving every request one place in line

When coders compete for dongles, each logical request needs one arrival number shared by both dongle queues. The number gives FIFO arbitration a stable order and lets EDF use arrival order to break equal-deadline ties. A simulation-wide counter ensures that a request does not get a different identity depending on which dongle is considered.

`take_ticket` reads and advances `next_ticket` while holding `ticket_mutex`. Calls therefore behave as one serialized sequence even when several coder threads ask at once:

```text
call A ─┐                  tickets: 0, 1, 2, ...
call B ─┼─ ticket_mutex →  one counter → unique request order
call C ─┘
```

For example, three successful calls starting from zero produce:

| Call | Ticket returned | Counter afterwards |
|---|---:|---:|
| 1 | 0 | 1 |
| 2 | 1 | 2 |
| 3 | 2 | 3 |

The counter is bounded so incrementing cannot overflow: values from zero through `LONG_MAX - 1` may be issued, and `LONG_MAX` means exhausted. A negative counter is treated as corrupted state. In either failure case the output remains untouched. The output is also written only after the mutex unlock succeeds, so callers observe a ticket only for a fully successful operation.

The ticket mutex is a leaf lock. Callers must obtain the ticket before locking dongles; no coder, stop, log, or dongle mutex is acquired by this operation. This keeps the global ordering counter independent of the per-dongle arbitration critical section.

<!-- section: planning -->
## How it was planned

The approved scope adds `take_ticket` to the simulation-state adapter, declares it in the State section of the shared header, and registers its source in the build. Acceptance criteria cover sequential allocation, counter boundaries and exhaustion, concurrent uniqueness and per-thread order, and NULL inputs. Lock and unlock failure paths are reviewed in source because they cannot be forced deterministically. The contract also records the lock-order requirement that the caller requests a ticket before acquiring any dongle mutex.

<!-- section: execution -->
## How it was executed

The implementation validates both pointers before locking, performs the counter read, bounds check, and increment under only `ticket_mutex`, and keeps the candidate in a local variable until unlock has succeeded. This preserves caller output on every failure path and prevents overflow. The implementation uses the simulation-owned counter and mutex initialized by `init_simulation`; it adds no allocation, clock access, or output.
