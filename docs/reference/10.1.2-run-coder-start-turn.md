## Put the offset before the first request

The start offset only helps if it happens before a coder enters dongle arbitration. `run_coder` therefore calls `sleep_start_turn` once, before its request loop. Odd seats proceed immediately; even seats wait for the configured `START_TURN_MS` delay. After that point, all coders use the same request and arbitration path.

The sequence is:

```text
run_coder
  ├─ initialize local held state
  ├─ sleep_start_turn once
  ├─ if the wait succeeded: enter the existing request/compile cycle
  └─ on stop or error: release_run with the current held state and result
```

If the simulation is already stopped during the offset, the coder exits without taking a ticket. If the clock operation fails, its error follows the existing failure route and also exits before requesting dongles. The offset is a scheduling heuristic: a one millisecond wait can encourage odd seats to queue first, but the operating system does not guarantee that order. The measured parallel-start runs are therefore evidence about observed behavior, not an acceptance promise.

For example, with five seats, seats 1, 3, and 5 can request immediately while seats 2 and 4 wait briefly. Once requests arrive, FIFO/EDF priority, dongle locking, logs, and the burnout clock retain their existing contracts. A one-coder simulation still follows its normal first-request and burnout behavior.

<!-- section: planning -->
## How it was planned

The approved scope adds the call to `run_coder` in `coders/src/coder/run_coder.c`; the living README is updated at close. Acceptance criteria cover the even-seat stopped path (no ticket), odd-seat stopped path (reaches its request), clock-error routing, and the one-coder binary log. Parallel-start scenarios are empirical diagnostics, since the phase plan does not treat thread start order as guaranteed. This subtask depends on [[docs/plan/phase-10-hardening-and-readme/10.1.1-sleep-start-turn.md|10.1.1]], which supplies the helper and its `START_TURN_MS` setting.

<!-- section: execution -->
## How it was executed

The helper result initializes the routine result before the loop. The loop runs only when that result is success, and all exits converge on `release_run` with the current `held` flag. This preserves the existing cleanup contract for stop and error while ensuring no request is made after a failed or interrupted start wait. The call is made once rather than once per cycle, so later compile/debug/refactor rounds are unchanged. No arbitration rule or shared state was added.

The recorded empirical runs observed burnout in 1/10 runs at `5 800 200 200 200 3 0 edf` and 0/10 at `5 1000 200 200 200 3 0 edf`. The first configuration is below the plan's sufficient viability bound, so its result is diagnostic and does not establish a guarantee.

<!-- section: problems -->
## Problems & resolution

The phase review initially found that mandatory startup acceptance cases relied on a one millisecond scheduling assumption. The phase plan was revised so deterministic stopped-state and injected clock-error checks establish call order and error handling, while the parallel-start runs remain empirical evidence. This avoids making machine scheduling part of the pass condition.
