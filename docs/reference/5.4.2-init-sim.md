## Constructing the simulation as one resource

A simulation combines ordinary configuration and runtime state with several independently owned resources. Its three coordination mutexes protect stop state, log output, and request tickets. Each dongle owns a mutex, condition variable, and request heap; each coder owns a mutex and points back to its simulation. `init_simulation` is the outer constructor that connects these pieces.

Construction follows the dependency order, and cleanup follows the reverse order:

```text
validate input
    ↓
copy config; reset start, stop, ticket and array fields
    ↓
stop mutex → log mutex → ticket mutex
    ↓
dongle array → coder array

failure after mutex setup → free_sim → coder array → dongle array
                                      → ticket → log → stop mutex
```

For example, with four coders, success creates four dongles and four coder records. The coders receive ids 1 through 4 and the ordered neighboring dongle pairs from the seat mapping. Each dongle begins available, with no release timestamp and an empty heap of capacity two. `start_ms` is zero because the later thread-start phase sets the clock origin when execution begins.

The function returns `0` only when the whole structure is ready. Invalid pointers or a coder count below one return `-1` before changing the destination. If resource creation fails later, rollback consumes every successfully initialized resource and returns `-1`; the caller must not call `free_sim` after that failure. On success, the caller owns the simulation resources and releases them once, after worker threads have been joined, with `free_sim`.

The destination must not own live resources before initialization. The configuration is read-only and copied into the simulation. A one-coder simulation has one dongle, so its two mapped indices are both zero.

<!-- section: planning -->
## How it was planned

The approved scope adds the whole-simulation initializer, its public declaration, and its deliverable build entry. Acceptance criteria map to six public API checks: complete initial state, one and large coder counts, integration with stop-state functions, initialization over sentinel-filled storage, invalid-input preservation, and reuse after cleanup. Failures in mutex or array construction cannot be forced portably by the oracle, so their reverse rollback sequence is a source review check. The spec depends on 5.4.1 so `free_sim` is available as the common rollback path.

<!-- section: execution -->
## How it was executed

The adapter validates before writing, initializes plain fields and NULL array pointers, then creates the stop, log, and ticket mutexes in order. A local helper destroys only the mutexes already created if that stage fails. It then delegates array construction to `init_dongles` and `init_coders`; either failure is handled through `free_sim`, which skips NULL arrays and releases the remaining resources in reverse dependency order. No thread, clock, lock acquisition, or output is part of construction.

The public function is named `init_simulation`. The shorter proposed name conflicted with local helper names in seven sealed phase 03 acceptance files, so the approved phase and subtask plans were updated and re-gated before implementation review.

<!-- section: problems -->
## Problems & resolution

The initial `init_sim` name collided with static helpers in existing acceptance tests. The phase review requested renaming the public API to `init_simulation`, removing the stale source, and re-sealing the oracle through the plan and phase gates. Those changes were completed before this close.
