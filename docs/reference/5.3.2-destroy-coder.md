## Releasing a coder's synchronization resource

A coder record combines ordinary simulation data with one operating-system resource: its mutex. Teardown must release that resource while leaving the record's values alone. The simulation pointer is borrowed, the thread handle belongs to thread lifecycle management, and the identity, dongle indices, and compile counters remain useful data until the owning coder array is freed or reused.

The lifecycle is:

```text
init_coder          coder in use                 destroy_coder
     │                    │                            │
     └── create mutex ────┴── no users remain ─────────┴── destroy mutex
```

The precondition is that initialization succeeded, the mutex is unlocked, and no thread can access it again. In the full simulation, callers satisfy the last condition by joining the coder and monitor threads before cleanup. Destroying a mutex still in use is not a supported recovery path; it violates the lifecycle precondition.

The return value reports the teardown operation:

| Call | Result | Effect |
|---|---:|---|
| `destroy_coder(&coder)` with a live, unlocked mutex | `0` | Destroys only `coder.mutex` |
| `destroy_coder(NULL)` | `-1` | No access occurs |
| Mutex destruction reports an error | `-1` | Other coder fields are not changed |

For example, after a successful destroy, `id`, `compile_count`, and `sim` keep their prior values. Reinitializing the same record then creates a new mutex and assigns fresh field values. A second destroy is valid only after that reinitialization; destroying an already-destroyed POSIX mutex is undefined behavior.

<!-- section: planning -->
## How it was planned

The approved scope was one cleanup adapter function plus its declaration and build registration: `coders/src/cleanup/destroy_coder.c`, `coders/main.h`, and `coders/Makefile`. The acceptance criteria cover successful destruction, preservation of every non-mutex field, reuse after reinitialization, and null input. A mutex-destroy failure is covered by source review because forcing destruction of a locked mutex would be undefined behavior. The sealed spec also required the cleanup layer map to mention coder mutex teardown.

<!-- section: execution -->
## How it was executed

The function validates the pointer before dereferencing it, delegates the one resource operation to `pthread_mutex_destroy`, and maps the pthread result to the project’s `0`/`-1` convention. Keeping teardown limited to the mutex preserves ownership boundaries: it neither joins the thread nor frees the borrowed simulation pointer or resets plain data. `init_coder` remains responsible for creating a fresh mutex when the same struct is reused.
