## Distinguish a normal stop from a runtime failure

A coder thread receives several helper results while running its compile and rest cycle. The result carries the cause: `0` means continue, `1` means the simulation stopped normally, and `-1` means a helper failed. Treating every nonzero value as an error would incorrectly mark an ordinary shutdown as a failed simulation; checking the shared stop flag afterwards can lose a real error if another thread stops the run at the same time.

| Result | Interpretation | Coder action |
|---|---|---|
| `0` | Work completed successfully | Continue the cycle |
| `1` | Normal stop observed | Release any held dongle once and return |
| `-1` | Runtime failure | Record `failed`, release any held dongle once, stop the simulation, and wake dongle waiters |

The result flows through the cycle without being collapsed:

```text
helper result
   ├─ 0  → next step
   ├─ 1  → release held resources → return normally
   └─ -1 → set_failed → release held resources → set_stopped → wake waiters
```

Recording failure before requesting a stop preserves the error even when other threads are already stopping. Cleanup is attempted once; a release failure on an otherwise normal exit is itself promoted to a runtime failure. The public thread routine returns `NULL` on every path.

<!-- section: execution -->
## How it was executed

The cycle helpers preserve the first nonzero sleep result so stop and failure remain distinguishable. The one-coder wait also uses the sleep result directly rather than inferring the cause from a later stop-state read. A shared exit helper handles both outcomes: normal exits release held dongles and return, while failures call `set_failed` before resource cleanup, stop, and wake-up. Each release is attempted once, and a failed release upgrades a normal exit to failure.

## Problems & resolution
