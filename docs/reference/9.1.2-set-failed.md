## Record failure separately from stopping

A simulation has two different questions to answer: did an internal operation fail, and should worker threads stop? The `failed` flag records the first; `stopped` remains the coordination signal for the second. Keeping them separate allows the monitor or a worker to report an error without changing the normal stop protocol itself.

`set_failed` serializes the write with `stop_mutex`, the mutex already protecting simulation-wide end state:

```text
lock stop_mutex
    failed = 1
unlock stop_mutex
```

A successful call returns `0`, including repeated calls, so setting the flag is idempotent. A lock error returns `-1` before changing the flag. If unlocking fails, the flag has already been set and the function returns `-1`; it does not roll the state back. The function does not acquire `log_mutex`, print, stop the simulation, or wake waiters. Its callers own the larger recovery sequence: record failure, request stop, then wake waiters.

This lock choice avoids coupling failure recording to output. It also preserves the existing lock order: code that already holds `log_mutex` may enter a path that takes `stop_mutex`, while `set_failed` introduces no reverse edge. The run coordinator reads `failed` after joining its created threads, so it observes the final outcome before cleanup and exit-status selection.

<!-- section: planning -->
## How it was planned

Subtask 9.1.2 adds one state-adapter operation. Its sealed `files:` list names `coders/src/state/set_failed.c`, the State declaration in `coders/main.h`, and the source list in `coders/Makefile`. Acceptance criteria cover setting and repeating the flag, recording it after a normal stop, releasing the lock, operating while another thread owns `log_mutex`, preserving state on a lock failure, concurrent writers and stop-state readers, and producing no output. The failure to unlock after a successful lock is not safely inducible with valid use and remains a source-review check.

<!-- section: execution -->
## How it was executed

The implementation uses only `stop_mutex` around the flag write. It returns immediately when locking fails, and reports an unlock failure without undoing the write. This keeps the function a small state operation; callers retain responsibility for stopping and waking the run even when one recovery step reports an error. No cross-cutting architecture or convention change was needed.
