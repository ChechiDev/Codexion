## Give the simulation a place to record failure

A simulation needs to distinguish a normal stop from a runtime failure. A burnout or a completed compile target ends the run normally; a failed clock, mutex, output write, or sleep operation means the run could not complete reliably. The existing `stopped` flag answers only whether the run should stop, so it cannot also communicate why.

The simulation context now holds a separate `failed` flag. Initialization sets it to zero before starting any thread or allocating resources. Later lifecycle work can set it when an internal error occurs, while preserving `stopped` as the coordination signal.

```text
init_simulation  →  failed = 0, stopped = 0
runtime error   →  failed = 1, stopped = 1
normal end      →  failed = 0, stopped = 1
```

The context also holds the monitor's `pthread_t`. Coders already keep their thread handles in their own records; this field gives the monitor the corresponding home in shared simulation state. It is meaningful after a successful `pthread_create`, so initialization leaves it untouched instead of inventing a non-portable sentinel value.

While threads are active, later work synchronizes writes to `failed` with `stop_mutex`. The run coordinator reads the result only after successfully joining every created thread; successful joins establish the required synchronization before teardown or exit-status selection.

<!-- section: planning -->
## How it was planned

Subtask 9.1.1 is the data-only first step of lifecycle task 9.1. Its sealed spec declares `coders/main.h` and `coders/src/init/init_simulation.c`: add `failed` and `monitor` to `t_sim`, and clear `failed` during valid initialization. Acceptance criteria cover dirty-storage initialization for one and four coders, compile-time member types and monitor-handle use, and unchanged invalid-argument returns. The spec explicitly leaves `monitor` untouched and keeps `free_sim` unchanged.

<!-- section: execution -->
## How it was executed

The fields were added to the existing simulation state, with `failed` initialized alongside the other scalar state after argument validation and before mutex setup or allocation. This ordering means a later initialization failure still leaves the failure result initialized. The monitor handle is written by the later thread-start operation, which knows whether thread creation succeeded; the initializer does not attempt to initialize an opaque thread identifier.

<!-- section: problems -->
## Problems & resolution

The first plan review requested a correction because the acceptance criteria expected a dongle release timestamp of zero, while the established initializer contract uses `-1` for an unreleased dongle. The spec and sealed acceptance oracle were corrected to preserve that existing contract, and the plan gate was rerun successfully. No implementation issue remained.
