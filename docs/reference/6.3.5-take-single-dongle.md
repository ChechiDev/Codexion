## Acquiring the lone coder's dongle

When a simulation has one coder, its two seat indices both identify dongle 0. The pair-acquisition operation cannot handle that representation: it requires two distinct resources and takes two locks. `take_single_dongle` gives the one-coder case its own path while keeping it inside the same arbitration rules as pair acquisition.

The operation builds one FIFO or EDF request, locks the single dongle once, and queues the request once. It then checks stop and readiness while holding the mutex. A request can take the dongle only when it is at the queue head, the dongle is available, and its cooldown has elapsed. Otherwise it sleeps on that dongle's condition variable for a bounded 1 ms slice and checks again.

```text
build request → lock dongle 0 → enqueue once
                         |
                  stopped? ── yes → unlock, taken = 0
                         |
                    ready? ── yes → pop, mark taken, unlock, taken = 1
                         |
                timed condition wait → retry
```

The stop check and condition wait use the same mutex. Since `pthread_cond_timedwait` atomically releases that mutex as it sleeps, a stop waker cannot broadcast between an unprotected stop check and sleep without the caller either seeing the stop state or receiving the wake-up.

The result is an output parameter that is assigned only on success:

| Return | `*taken` | Dongle state |
|---|---:|---|
| `0` | `1` | Acquired; mutex released for the caller. |
| `0` | `0` | Simulation stopped; no acquisition. |
| `-1` | unchanged | Invalid input or fatal failure; no mutex remains held when cleanup succeeds. |

After a request has entered the heap, an operational failure cannot safely discard it. The failure path therefore releases the lock, marks the simulation stopped, and wakes dongle waiters so the run can terminate rather than letting a stale queue entry block scheduling. A stop-mutex error follows the established `is_stopped` contract and is treated as stop. The caller owns user-facing logging and any wait after taking the dongle; those belong to the coder flow in the later phase.

<!-- section: planning -->
## How it was planned

The approved scope adds one orchestration function in `coders/src/dongle/take_single_dongle.c`, its Dongle API declaration in `coders/main.h`, and the source entry in `coders/Makefile`. Acceptance criteria cover initial acquisition, cooldown under FIFO and EDF, exactly one queued request while blocked, wake-up on stop, and invalid inputs. The spec assigns build, Norm, and otherwise hard-to-force failure paths to code review.

<!-- section: execution -->
## How it was executed

The implementation keeps the one-resource flow separate from pair acquisition so it never duplicates a lock, queue insertion, pop, or state update. It reuses `build_request`, `is_dongle_ready`, the absolute-deadline adapter, the stop state, and the dongle wake operation. The timed wait is performed directly with the single dongle mutex; the pair wait helper is not needed. Once queued, fatal errors trigger stop and broadcast cleanup. The change also registers the source and public prototype.

<!-- section: problems -->
## Problems & resolution

The code review found that the failed-push cleanup path did not check whether unlocking the dongle mutex succeeded. The implementation was revised to treat an unlock failure as fatal, then set stop and wake waiters; the second code review approved the corrected path.
