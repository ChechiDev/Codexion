## Turning a scheduling policy into a priority key

The request key is the policy-specific value that the priority queue compares
first. The comparator in [[docs/reference/4.1.1-is-request-before.md]] then
uses the arrival ticket to break equal-key ties. Keeping those two steps
separate lets the heap use one ordering rule for either scheduler.

| Mode | Key | Example | Meaning |
|---|---|---|---|
| FIFO | `ticket` | ticket `7` → key `7` | Earlier arrivals have smaller keys. |
| EDF | `last_compile_start + time_to_burnout` | `1000 + 410` → key `1410` | The request with the earlier deadline has the smaller key. |

For EDF, both the previous compilation start and the resulting deadline use
milliseconds elapsed from the shared simulation start. Before the first
compilation, the start value is zero. The burnout duration is a positive
millisecond count. A ticket is not part of the EDF deadline; it only resolves
two requests whose deadlines match.

```text
FIFO request: ticket=7                         → key=7
EDF request:  last start=1000, burnout=410    → key=1410
EDF tie:      same deadline, tickets 7 and 8  → ticket 7 precedes
```

The function returns `-1` for invalid input or an EDF sum that cannot fit in a
`long`. It checks the upper bound before addition, so signed overflow never
occurs. It does not clamp an oversized deadline: clamping would make distinct
deadlines appear equal and could change arbitration order. Every valid result
is nonnegative, which keeps the error value distinct from a usable key. Callers
must check for `-1` before building or enqueueing a request in either dongle
heap.

This is pure core policy logic: it needs no clock, lock, output, allocation, or
global state. The function returns its value directly; using an out parameter
would exceed the project's four-parameter Norm limit.

storage and operations were explicitly left to later subtasks.

<!-- section: execution -->
## How it was executed

The implementation validates the ticket and mode, returns the ticket directly
for FIFO without consulting EDF time inputs, and validates EDF's nonnegative
start and positive duration before checking
`last_compile_start <= LONG_MAX - time_to_burnout`. Only after that guard does it form
the deadline. This keeps
the policy arithmetic centralized while leaving equal-key ordering to the
existing comparator. The `policy/` row in [[docs/architecture.md]] now names
both key calculation and request ordering.
