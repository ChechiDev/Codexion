## Waking condition-variable waiters without losing a stop signal

`wake_dongles` sends a broadcast on each dongle's condition variable. Its job is to let threads blocked while waiting for a dongle re-check the simulation stop state and exit. The function does not decide whether the simulation should stop; its caller first sets that state.

A condition-variable notification is not stored for a future waiter. The shared mutex closes the gap between checking the predicate and going to sleep:

```text
waiter: lock dongle → check stopped → cond_wait (atomically releases lock)
waker:                    lock dongle → broadcast → unlock
```

If the waker gets the mutex first, the waiter subsequently sees `stopped` and does not sleep. If the waiter gets there first, it enters `cond_wait` and the broadcast wakes it. In either ordering, the stop notification cannot fall into the gap between predicate check and wait.

The caller's protocol is therefore:

```c
set_stopped(sim);
wake_dongles(sim);
```

A broadcast while the simulation is still running is harmless: waiters wake, re-check their condition, and can wait again. The wake-up routine leaves the stop flag and all dongle state intact.

For each dongle, the function holds only that dongle's mutex during its broadcast and releases it before moving to the next one. This avoids holding multiple dongle locks together and lets all waiters on a given dongle wake, rather than selecting just one. Invalid simulation or missing dongle storage returns `-1`. A pthread failure also makes the overall result `-1`; processing continues for later dongles so one failure does not suppress other wake-ups.

<!-- section: planning -->
## How it was planned

Subtask 6.3.1 assigns one orchestration operation to `coders/src/dongle/wake_dongles.c`, declares it in the Dongle section of `coders/main.h`, and adds the source to `coders/Makefile`. The approved acceptance criteria cover stop wake-up across all dongles, multiple waiters on one dongle, a repeated check-to-wait race, unchanged state and unlocked mutexes, the one-coder case, and invalid input. Lock, broadcast, and unlock failure paths are reviewed in source because tests cannot force them deterministically.

<!-- section: execution -->
## How it was executed

The implementation factors the per-dongle lock, broadcast, and unlock into a helper, then walks the configured dongle array in index order. It attempts the unlock even if broadcasting fails, records any failure, and continues to later dongles. Each critical section contains just one dongle mutex. The orchestration layer uses the simulation's existing condition variables and state; it allocates nothing and does not change the stop flag, availability, cooldown timestamp, or request heap.

The `dongle/` architecture entry now records this stop wake-up responsibility alongside request construction. No cross-cutting convention changed.
