## Waiting without holding both dongles

A coder can be at the head of its requests but still be unable to compile: a dongle may be in use or cooling down. The caller enters `wait_for_dongles` while holding both dongle mutexes in increasing index order. A bounded condition wait gives another thread a chance to change dongle state without spinning or losing the existing lock-order rule.

`pthread_cond_timedwait` can atomically release and reacquire only the mutex passed to it. The function therefore first releases the second dongle mutex, then waits on the first dongle's condition variable and mutex for a 1 ms slice:

```text
caller holds:       [first mutex] [second mutex]
release second:     [first mutex] [free]
timed condition wait: [released by pthread_cond_timedwait] [free]
return from wait:   [first mutex] [free]
reacquire second:   [first mutex] [second mutex]
```

The first mutex remains held between the caller's stop check and the condition wait, so a stop broadcast using that condition cannot slip through this handoff. A signal on the first dongle wakes the caller promptly; changes to the second dongle are noticed when the short slice expires. A wake-up and a timeout both mean “recheck the shared state” and return success with both mutexes held. The function does not decide whether either dongle is ready; the caller owns that policy.

The caller must preserve the contract on every path:

| Result | Mutexes on return | Meaning |
|---|---|---|
| `0` | Both held, first then second | Recheck stop and readiness; a wake or timeout is normal. |
| `-1` for invalid input | No locks touched | The supplied coder/simulation/dongles or distinct ordered pair is invalid. |
| `-1` for a runtime failure | Locks released as far as cleanup permits | Follow the orchestration fatal-stop path. |

This bounded wait is part of the overall scheduling latency budget. With integer-millisecond cooldowns, a blocked request has at least a 1 ms cooldown remaining; the slice is not longer than that. `get_deadline` supplies the absolute deadline expected by the condition API.

<!-- section: planning -->
## How it was planned

The approved spec placed this operation in dongle orchestration and declared three production files: the implementation, the public prototype in `coders/main.h`, and its source entry in `coders/Makefile`. Acceptance criteria cover a timed return with both locks restored, proof that the second mutex is available during the wait, repeated use without leaks, and invalid input that touches no lock. The spec also fixes the caller precondition and failure ownership contract so that the later acquisition loop can recheck state consistently.

<!-- section: execution -->
## How it was executed

The implementation validates pointers and the ordered, distinct dongle pair before touching synchronization state. It builds a 1 ms absolute deadline through the time adapter, unlocks the second mutex, performs the condition wait on the first, and reacquires the second only after a normal wake or timeout. This retains the global lower-index-first lock order. On a runtime error it attempts to release the mutexes still owned and returns `-1`; the caller handles the fatal stop and wake-up sequence. No shared readiness fields, request heaps, allocation, logging, or policy calculations belong in this wait primitive.

<!-- section: problems -->
## Problems & resolution

The first code review found that cleanup after failure to unlock the second mutex did not attempt that second unlock again before releasing the first. The cleanup helper was corrected to attempt release of every mutex still considered held; the subsequent code review approved the change. As the review notes, a pthread mutex failure can still prevent cleanup from guaranteeing recovery.
