## A dongle as a synchronized request resource

A dongle sits between two neighboring coders. Each neighbor can have one request waiting for it, so its scheduling heap needs exactly two slots. The heap orders those requests using the policy key and tie-breaking rules defined by the core policy module; the dongle initializer only establishes the storage and synchronization needed to use that heap safely.

The dongle groups four pieces of state:

| Field | Initial meaning |
|---|---|
| `mutex` | Protects the heap, availability, and release timestamp. |
| `cond` | Lets waiters sleep for a change to this dongle (used by later simulation phases). |
| `heap` | Holds up to the two neighbors' requests. |
| `available` | `1`: nobody currently holds the dongle. |
| `released_at` | `-1`: it has never been released, so its first use has no cooldown. |

After successful initialization, the state can be pictured as:

```text
             mutex
               │ protects
     ┌─────────┴─────────┐
     │                   │
 available = 1       released_at = -1
     │
     └── heap: [request, request]  (capacity 2)
               ▲
               │ condition variable wakes waiters
              cond
```

For example, two neighboring requests can occupy the heap, and a third cannot:

```text
push(A) → 0     push(B) → 0     push(C) → -1
head      → the earlier request according to the configured policy
```

The `-1` timestamp is a sentinel, not a time value. Once a coder releases the dongle, later simulation code records elapsed milliseconds from the simulation start (`0` or greater), allowing cooldown checks to use the same clock base as scheduling deadlines.

Initialization is a small resource transaction: create mutex, create condition variable, allocate the capacity-two heap, then publish the usable state. If a step fails, only completed steps are undone, in reverse order. A failed call therefore leaves no owned resources, though the bytes in the struct are unspecified. The caller must provide writable storage that owns no live resources and owns all three resources after a successful return.

## How it was planned

Subtask 5.2.1 is the first dongle lifecycle step in task 5.2. Its approved scope declares `t_dongle`, `init_dongle`, and the build entry for the new adapter source. The acceptance criteria cover initialized defaults, an unlocked mutex, a functioning condition variable, capacity and request ordering, independence between instances, and NULL rejection. Failure-path rollback is checked by code review because the test harness has no portable way to force pthread initialization or allocation failures.

<!-- section: execution -->
## How it was executed

The adapter follows the ownership boundary from the plan: it owns mutex, condition-variable, and heap setup, and delegates heap allocation and initialization to the existing heap API. The sequence makes rollback explicit and prevents publishing `available` or `released_at` until every resource is ready. No previous struct field is needed, so callers do not need to zero storage first. Successful callers retain ownership and later teardown is handled by the paired dongle cleanup subtask.

The `init/` adapter row in [[docs/architecture.md]] now records this lifecycle responsibility and its dependencies.
